# 0.2.0 Management MCP Catalog System Capability

Date: 2026-07-07
Branch: `codex/system-info-management-mcp-catalog-capability`

## Objective

Make the management MCP tool-catalog metadata contract visible in the public API compatibility contract before the console attempts automated admin-agent diagnostics or writes.

## 中文说明

连接诊断会读取 Management MCP 的 `tools/list`，并检查 `metadataVersion: 4`、`safety`、`access`、`lifecycle`、`execution` 和写工具确认参数 schema。但如果控制台连接到旧后端，最好在 API 兼容检查阶段就提示“后端不支持当前管理工具目录契约”，而不是等到连接诊断单独调用 Management MCP 后才失败。本轮把这项要求加入 `GET /api/v1/system/info` 的 capability 列表。

## Contract

`GET /api/v1/system/info` now includes:

- `management_mcp_tools_metadata_v4`

The web console lists the same value in `requiredConsoleCapabilities`, so `checkApiHealth` reports `api_contract_incompatible` when an older backend does not advertise this contract.

The response also includes `managementMcpToolCatalog`, a static compatibility summary:

```json
{
  "metadataVersion": 4,
  "requiredMetadata": ["safety", "access", "lifecycle", "execution"]
}
```

This summary intentionally does not expose the live protected Management MCP tool list. It gives admin agents and web-console compatibility checks a stable public hint before they request `/api/v1/management/mcp`.

The console checks the summary through a pure `systemInfoContractIssues` helper before treating API health as compatible. This catches three cases before an admin-agent workflow starts:

- the backend does not return the summary;
- the backend advertises an unsupported catalog metadata version;
- the backend omits required catalog metadata fields such as `safety` or `access`.

When the only compatibility problem is this Management MCP catalog contract, connection diagnostics and preflight panels use `message.apiContractIncompatibleManagementCatalog` instead of rendering raw field names such as `managementMcpToolCatalog.requiredMetadata.access`.

For regular missing console capabilities, the UI keeps `permission_package_*` and `management_mcp_tools_metadata_v4` as the machine contract but renders localized module names in diagnostics and preflight panels. Operators see labels such as "Permission approval queue" or "上线状态检查" instead of raw capability keys.

If a future or unknown system-info contract issue cannot be mapped to a known capability label, diagnostics and preflight panels use `message.apiContractIncompatibleUnknown` rather than echoing the raw `system info contract issues: ...` message.

The capability label map is centralized in `frontend/src/systemCapabilityLabels.ts` and is covered against every `requiredConsoleCapabilities` entry. Both diagnostics and health-check presentation import that shared map, so adding a new required console capability without English and Simplified Chinese operator labels fails the frontend test suite instead of leaking raw keys.

## Changes

- Added `management_mcp_tools_metadata_v4` to backend `systemCapabilities`.
- Added the same capability to frontend `requiredConsoleCapabilities`.
- Added `managementMcpToolCatalog` to the public system-info response and frontend `SystemInfo` type.
- Split the frontend system-info compatibility rules into `systemInfoContract.ts`, and made `checkApiHealth` block incompatible Management MCP catalog summaries.
- Added backend and frontend regression checks.
- Updated product docs and changelog in English and Simplified Chinese.
- Centralized frontend system-capability labels in one shared module and enabled explicit `.ts` source imports so Node-based tests and the Vite build exercise the same map.
