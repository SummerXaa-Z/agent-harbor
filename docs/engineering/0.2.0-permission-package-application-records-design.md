# Permission Package Application Records Design

## Goal

Make the AI Admin permission journey auditable after a package is applied. A non-technical administrator or admin agent should be able to answer: which template version was applied, who/what received access, which objects were created, and when the package was applied.

## Design Consensus

This slice adds a first-class `PermissionPackageApplication` record. It does not add a template management UI, mutable package templates, approval workflow, rollback workflow, or package diff viewer.

The record captures:

- immutable package identity: `applicationId`, `draftId`, `templateId`, `templateVersion`
- scope: `tenantId`, `workspaceId`, `targetId`, `callerInstanceId`, `subjectSelector`
- administrator intent: `requestText`, `region`
- applied evidence: allowed capability IDs/keys, entitlement IDs, workspace assignment IDs, instance assignment IDs
- applied data scopes
- timestamps: `appliedAt`

Built-in permission package templates get a stable integer `version`, starting at `1`. This is deliberately simple: the current product uses deterministic built-in templates, so recording the template version in each application record is enough to support first-release auditability.

## API Surface

REST management API:

- `POST /api/v1/permission-packages:apply` returns the existing apply response plus `application`.
- `GET /api/v1/permission-packages/applications?tenantId=&workspaceId=&templateId=&targetId=&callerInstanceId=&limit=` lists application records.

Management MCP:

- `list_permission_package_applications` lists the same records for admin agents.

The existing `permission_package.applied` audit event stays in place and references the application record ID in metadata. The application record is the structured review artifact; the audit event remains the generic event stream.

## Persistence

Add PostgreSQL migration `009_permission_package_applications.sql` with a `permission_package_applications` table. The in-memory repository mirrors the table shape so local demos and tests behave the same way as PostgreSQL.

The application record is written after the package's entitlements and assignments are created. This matches the current audit-event behavior and keeps this slice narrowly scoped. A future hardening slice can make package application fully transactional across created objects, application record, and audit event.

## Acceptance Criteria

- Applying a package returns a non-empty `application` object.
- Listing applications can filter by tenant subtree, workspace, template, target, caller instance, and limit.
- The application record includes template version, draft ID, created entitlement IDs, workspace assignment IDs, instance assignment IDs, allowed capability IDs/keys, and data scopes.
- Management MCP exposes `list_permission_package_applications`.
- Memory and PostgreSQL repositories round-trip the record.
- Existing permission package apply behavior remains compatible.
