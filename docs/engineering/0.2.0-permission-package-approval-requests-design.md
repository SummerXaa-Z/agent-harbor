# Permission Package Approval Requests Design

## Goal

Turn the policy gate from a dead end into a usable approval path. A non-technical administrator or admin agent should be able to draft a high-risk permission package, create an approval request, approve or reject it, and apply the same approved package with evidence.

## Design Consensus

This slice adds permission-package approval requests. It does not add custom approval routing, identity-provider roles, multi-step approvals, notifications, delegated approver groups, or rollback.

The approval request is a snapshot of a ready permission package draft that currently requires approval. It captures the exact draft identity, package template version, scope, allowed capability ids/keys, data scopes, and policy-gate reasons. This prevents approval drift: applying with an approval request must match the same draft and scope that was approved.

## States

- `pending`: request was created and is waiting for review.
- `approved`: request can authorize one or more matching apply attempts.
- `rejected`: request cannot authorize apply.

The first slice does not expire approvals or consume them after one apply. Those controls can be added after the product has approver roles and policy configuration.

## API Surface

REST management API:

- `POST /api/v1/permission-packages/approval-requests`: build a draft, require `readiness.canApply = true` and `policyGate.canApplyDirectly = false`, then create a `pending` approval request.
- `GET /api/v1/permission-packages/approval-requests?tenantId=&workspaceId=&templateId=&targetId=&callerInstanceId=&status=&limit=`: list requests by tenant subtree and filters.
- `POST /api/v1/permission-packages/approval-requests/{id}/approve`: mark a pending request approved.
- `POST /api/v1/permission-packages/approval-requests/{id}/reject`: mark a pending request rejected.
- `POST /api/v1/permission-packages:apply`: accepts optional `approvalRequestId`. Direct-apply packages still work without one. Approval-required packages require a matching approved request.

Management MCP:

- `create_permission_package_approval_request`
- `list_permission_package_approval_requests`
- `approve_permission_package_approval_request`
- `reject_permission_package_approval_request`
- `apply_permission_package` accepts optional `approvalRequestId`.

Frontend:

- AI Admin shows the latest approval request for the current draft.
- Approval-required drafts offer Create approval request instead of direct apply.
- Pending requests can be approved or rejected in the workbench.
- Approved matching requests enable Apply package.

## Validation Rules

Create approval request:

- Draft must be structurally ready.
- Draft must require approval.
- Store the current draft id and policy-gate reasons.

Apply with approval request:

- Request id must exist.
- Request status must be `approved`.
- Request draft id, tenant, workspace, target, caller, subject selector, template id/version, policy version, allowed capability ids, allowed capability keys, and data scopes must match the newly built draft.

Approve/reject:

- Only `pending` requests can be resolved.
- Resolution records reviewer and optional comment when provided.
- Each transition appends a management audit event.

## Acceptance Criteria

- Approval-required drafts can create approval requests.
- Direct-apply drafts cannot create approval requests because they do not need one.
- Applying an approval-required draft without an approval request still fails before any writes.
- Applying with a pending, rejected, missing, or mismatched approval request fails before any writes.
- Applying with a matching approved approval request succeeds and records the approval request id on the package application audit metadata.
- Memory and PostgreSQL repositories round-trip approval requests and filters.
- Management MCP can create, list, approve, reject, and apply with approval requests.
- AI Admin exposes the approval path in Chinese and English.
