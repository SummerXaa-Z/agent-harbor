# Permission Package Policy Gate Design

## Goal

Protect the AI Admin permission-package journey from silent over-granting before the first open-source release. A non-technical administrator or admin agent should be able to draft and understand a permission package, but direct application must stop when the allowed capabilities need human approval.

## Design Consensus

This slice adds a deterministic policy gate to each permission package draft. It does not add a full approval workflow, approver assignments, approval persistence, rollback, package version migration, or tenant-custom policy authoring.

The policy gate separates two decisions:

- `readiness`: whether the draft is structurally valid and internally consistent.
- `policyGate`: whether a ready draft can be applied directly or must be routed to approval first.

This keeps the product journey usable for low-risk read-only packages while protecting higher-risk changes. The most important first-release guarantee is that an admin can safely preview, explain, and apply low-risk packages without accidentally granting write, export, admin, sensitive, or high-risk access.

## Policy Rules

The built-in policy version starts at `1`. A permission package draft can be applied directly only when all allowed capabilities stay inside the direct-apply envelope:

- `read` action is directly applicable when the capability risk is `low` or `medium` and sensitivity is `public` or `internal`.
- `write`, `export`, `delete`, and `admin` actions require approval.
- `execute` requires approval unless the capability risk is `low`.
- `high` and `critical` risk capabilities require approval.
- `confidential` and `restricted` sensitivity capabilities require approval.

The gate reports capability-level reasons with stable `reasonKey` values so REST, MCP, and the web console can show consistent Chinese and English messages.

## API Surface

REST management API:

- `POST /api/v1/permission-packages/drafts` returns the existing draft plus `policyGate`.
- `POST /api/v1/permission-packages:apply` still requires `readiness.canApply`, and now also requires `policyGate.canApplyDirectly`.

Management MCP:

- `draft_permission_package` returns the same draft shape, including `policyGate`.
- `explain_permission_package_draft` includes `policyGate`, policy-gate summary text, and next actions.
- `apply_permission_package` refuses approval-required drafts through the same shared apply path.

Frontend:

- AI Admin shows policy-gate status next to readiness.
- Apply is disabled when approval is required.
- The local compatibility draft builder mirrors the backend policy-gate rules.

## Acceptance Criteria

- Low-risk internal read packages remain directly applicable.
- Ready drafts that include write, export, admin, high-risk, critical-risk, confidential, or restricted allowed capabilities return `policyGate.decision = "approval_required"` and `canApplyDirectly = false`.
- Applying an approval-required package returns a validation error and does not create entitlements, assignments, application records, or audit events.
- Management MCP explain output includes policy-gate reasons and next actions.
- AI Admin clearly shows approval-required status in Chinese and English and disables direct apply.
- Public docs explain that direct apply is intentionally limited to low-risk permission packages.
