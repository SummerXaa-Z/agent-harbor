# 0.2.0 Production Approval Scenario Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Add an executable local scenario that proves the v0.2.0 approval-required permission package journey from tenant setup through runtime evidence.

**Architecture:** Reuse the existing shell scenario pattern and dependency-free mock MCP server. The scenario creates a three-level tenant tree, discovers read/write/export MCP tools, drafts a support-ticket-triage permission package, creates and approves a matching approval request, applies the package with `approvalRequestId`, and verifies runtime allow/deny behavior plus access-profile, approval, application, and audit evidence.

**Tech Stack:** Bash, curl, Python JSON helpers, existing AgentHarbor REST API, existing `scripts/mock-mcp-server.py`, Makefile scenario targets.

### Task 2: Add the Approval-Required Permission Package Scenario

**Files:**
- Create: `scripts/scenario-permission-package-approval.sh`

- [x] **Step 1: Create the script from the existing scenario conventions**

Use the same helper functions as `scripts/scenario-core-journey.sh`: `need`, `request`, `expect_status`, `expect_2xx`, `json_get`, local mock MCP startup, and cleanup trap.

- [x] **Step 2: Create the live setup**

The script must create:

- root, child, and grandchild tenants
- a child-tenant local caller
- a short-lived Agent Key for the caller
- a root-tenant MCP target pointing at the local mock MCP endpoint
- refreshed capabilities for `search_customer`, `update_ticket`, and `export_contracts`

- [x] **Step 3: Verify the approval gate before applying**

The script must call `POST /api/v1/permission-packages/drafts` with template `support-ticket-triage` and assert:

- `readiness.canApply == true`
- `policyGate.decision == "approval_required"`
- `policyGate.canApplyDirectly == false`
- `update_ticket` is an allowed capability
- `export_contracts` is blocked

Then call `POST /api/v1/permission-packages:apply` without `approvalRequestId` and assert HTTP `400`.

- [x] **Step 4: Create, approve, and apply the approval request**

The script must call:

- `POST /api/v1/permission-packages/approval-requests`
- `GET /api/v1/permission-packages/approval-requests?...status=pending&limit=1`
- `POST /api/v1/permission-packages/approval-requests/{id}/approve`
- `POST /api/v1/permission-packages:apply` with the approved `approvalRequestId`

Assert the approval status transitions from `pending` to `approved`, and the apply response includes a permission package application with `templateId == "support-ticket-triage"`.

- [x] **Step 5: Verify runtime and evidence**

The script must:

- call `tools/list` and assert `update_ticket` is visible while `export_contracts` is filtered out
- call `export_contracts` and assert HTTP `403`
- call `update_ticket` and assert a `2xx` response
- fetch the child tenant access profile and assert grant, target, capability, workspace assignment, instance assignment, allowed trace, and denied trace counts are present
- list permission package applications and assert the new application exists with the approval-required template
- list audit events for `permission_package.applied` and assert the event metadata includes the approval request id and application id

- [x] **Step 6: Run the scenario against a local API**

Start the API with private upstreams enabled:

```bash
AGENT_HARBOR_ALLOW_PRIVATE_UPSTREAMS=true make run
```

Run the scenario in a second terminal:

```bash
make scenario-permission-package-approval
```

Expected: script exits with status `0` and prints that the permission package approval scenario is complete.
