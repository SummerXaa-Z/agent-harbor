# AgentHarbor v0.3.0 Access Handoff Release Notes

Status: draft. Do not tag or describe this release as ready until the required PostgreSQL, permission-package scenario, and full release gates pass on the final commit.

## Highlights

- Access Handoff turns a ready permission-package application into a bounded delivery view with capability and data-scope summaries, copyable MCP configuration, prompt guidance, one-time plaintext short-lived tokens, revocation, and audit references.
- Permission-package requests can now preserve an exact capability boundary from draft through approval, application, readiness, report, handoff, and token creation.
- Built-in permission-package templates are version 2 and fail closed unless capabilities have an explicit, template-compatible data-domain classification.

## Compatibility Contract

### Exact requests and legacy bundles

- A non-empty `requestedCapabilityId` means **exactly one requested capability**. Clients must send the same value at every stage that accepts it. Dropping the field later changes the lookup back to legacy bundle mode and must not match an arbitrary exact request.
- Omitting `requestedCapabilityId`, or sending an empty string, preserves the legacy template-bundle behavior. Existing clients therefore keep their previous request shape, but they do not gain the new exact-boundary provenance.
- Readiness and Access Handoff may treat a legacy application as exact-equivalent only when its stored `requestedCapabilityId` is empty, `allowedCapabilityIds` contains exactly the requested capability, and all current scope, template-version, data-scope, configuration-drift, runtime-evidence, and audit checks pass.
- Exact-equivalent lookup is read-only compatibility. It does not backfill the database or rewrite historical provenance; the legacy application remains a bundle-origin record with an empty `requestedCapabilityId`.

### Template v2 and capability classification

- All built-in templates now use version 2.
- Each capability must expose at least one explicit domain through `dataDomains` or `dataScopes[].dataDomain`.
- Every non-empty declared domain must equal the selected template's `defaultDataDomain`. Missing, unsupported, mixed, or contradictory domains are blocked rather than inferred from names or descriptions.
- Administrators can classify a capability in **Capability Governance**, or call `PATCH /api/v1/capabilities/{id}` with `dataDomains`. Current built-in domains are `crm`, `support`, `analytics`, and `audit`.

### Existing applications and handoff tokens

- Version-1 approvals and applications remain queryable for audit history, but they do not satisfy current version-2 production readiness.
- Handoff tokens tied to pre-v2 applications remain listable and revocable. Runtime validation rejects them for governed MCP tool calls after the template-version cutover.
- After upgrading, classify the relevant capabilities, preview the request again, re-approve it when policy requires approval, apply the v2 package, prove runtime evidence, and issue a new handoff token.

## PostgreSQL Migration

Migration `015_permission_package_requested_capability.sql` adds `requested_capability_id text not null default ''` to both permission-package approval requests and applications, plus partial lookup indexes for non-empty exact requests.

The migration is additive and intentionally performs no provenance inference or destructive backfill. Existing rows retain `''` and therefore remain legacy bundle records. With `AGENT_HARBOR_DATABASE_URL` configured, normal AgentHarbor startup applies forward migrations before the PostgreSQL repository begins serving requests.

For an instance or fleet upgrade:

1. Take the normal database backup or snapshot required by the deployment runbook.
2. Deploy the new binary and allow migration 015 to complete; finish the v2 binary rollout before minting new handoff tokens.
3. Classify capabilities that participate in permission packages and verify each classification matches its selected template.
4. Re-preview, re-approve when required, apply, and collect fresh runtime evidence for v2 applications.
5. Issue fresh handoff tokens, migrate consumers, and revoke the pre-v2 tokens after confirming the new path.

## API Notes

`requestedCapabilityId` is accepted by the permission-package draft/apply inputs and is persisted on approval requests and applications. The same optional boundary is available to approval/application listing, application health, production readiness, production report, Access Handoff, and handoff token creation. Management MCP tools expose the equivalent optional field.

The Access Handoff REST surface is:

- `GET /api/v1/permission-packages/access-handoff`
- `POST /api/v1/permission-packages/access-handoff/tokens`
- `DELETE /api/v1/permission-packages/access-handoff/tokens/{id}`

## Verification Required Before Tagging

Run the final release gates against the final commit:

```bash
git diff --check
make check
make test-postgres
make scenario-permission-package-approval
make release-check
```

The acceptance record must explicitly cover:

- exact `requestedCapabilityId` propagation from draft through handoff token and governed runtime call;
- omitted/empty legacy bundle behavior;
- the single-capability legacy exact-equivalent lookup without provenance mutation;
- missing, mismatched, and mixed data-domain rejection;
- v1 application readiness rejection and pre-v2 handoff-token runtime rejection;
- migration 015 against PostgreSQL, including existing rows that remain empty-string legacy records.

## Known Limits

- My Access self-service, long-lived credentials, and multi-resource permission packages remain outside this slice.
- Access Handoff does not expand authorization; live capability, subject, template-version, and data-scope checks remain authoritative at runtime.
- Historical provenance is intentionally not inferred. Operators that need exact-boundary provenance must create and apply a new exact v2 request.
