## Compatibility and Safety Coverage

| Release contract | Acceptance record |
| --- | --- |
| Exact requested capability | `requestedCapabilityId` is retained through draft, approval, apply, application, readiness, report, handoff, token creation, filtered `tools/list`, and governed runtime call. A sibling capability that is otherwise authorized by a normal key remains unavailable to the handoff token. |
| Legacy bundle request | Omitted or empty `requestedCapabilityId` remains the legacy template-bundle lane and does not match an arbitrary exact application. |
| Legacy exact equivalence | A legacy application is accepted for an exact read only when its immutable allowed set contains exactly the requested capability and its template, scope, subject, region, keys, data scopes, freshness, runtime records, and audit state match. Provenance is not rewritten. |
| Data-domain enforcement | Missing, unsupported, mixed, contradictory, and template-denied domains fail closed. Capability classification persists across MCP refresh. |
| Template cutover | Version-1 applications remain auditable but do not satisfy version-2 readiness. Pre-v2 Access Handoff tokens remain listable and revocable but fail governed runtime authorization. |
| Atomic apply boundary | Memory and PostgreSQL reject capability or approval snapshot drift before writes. PostgreSQL row locks bind the current capability snapshot; conflicts roll back approval consumption, grants, application, and audit writes. |
| Token boundary | Wrong subject, wrong target, stale template, stale capability, disallowed tool, generic MCP method, and OpenAPI route all fail closed before upstream use. |
| PostgreSQL upgrade | Migrations 014 and 015 run against PostgreSQL; existing exact-capability fields remain empty-string legacy provenance unless a new exact request is created. |

## Upgrade and Rollback Review

- The release notes document the required order: backup, apply migrations 014 and 015, complete the v0.3 binary rollout, classify capabilities, re-preview/re-approve/apply, collect runtime records, issue fresh tokens, migrate consumers, and revoke old tokens.
- Before a binary rollback, operators must stop issuance and revoke all v0.3 Access Handoff tokens while v0.3 is still running. The additive 014 and 015 schema is retained.
- Permission rollback is separate from schema rollback and requires reviewed remediation of the created entitlement and assignment objects.
