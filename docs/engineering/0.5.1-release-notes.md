# AgentHarbor v0.5.1 Release Notes

Status: released 2026-10-01. Patch release on top of v0.5.0: the two fixes
from external evaluation round 6 plus the round-6 evaluation archive (PR
#411). Frontend-only; no schema changes, no migrations, no API contract
changes, no backend changes.

## Highlights

- Go-live runtime validation no longer dead-ends on a mismatched deny probe
  (round 6, finding #41, PR #411). When the caller holds a pre-existing
  grant wider than the package, the blocked capability sails through the
  gateway instead of returning 403 — the old sequence aborted right there,
  so the allowed call was never made and readiness sat at 9/11 with no
  explanation. The mismatch is now a diagnosed condition: the allowed probe
  always runs (its record lands, readiness advances to 10/11) and the
  console names the capability that was let through, the observed versus
  expected status (got HTTP 200, expected 403), and the recovery path —
  narrow the conflicting grants and re-run. A second notice states plainly
  that the denied-call readiness check stays blocking until that happens.
  New `classifyRuntimeValidationRun` model distinguishes
  tool-list-failed / allowed-failed / deny-unexpected / completed outcomes.
- The cockpit fix-guidance modal for unreachable targets carries each
  target's classified probe failure (round 6, finding #42, PR #411) — for
  example `Retired MCP (http://127.0.0.1:59999/mcp) — UPSTREAM_CONNECT_ERROR:
  upstream connection failed: dial tcp …: connection refused` — matching the
  registry test-connection modal instead of showing only the name and
  endpoint.
- The round-6 external evaluation record is archived with same-day triage
  in `docs/product/0.4.0-console-eval.md`: verdict 有条件通过 (conditional
  pass) on the released v0.5.0 baseline, time-to-first-report 25m14s
  end-to-end (9m21s clean re-walk) against the 30-minute goal, both
  notification phase-2 specializations passed strongly, all thirteen
  regression checks (R1–R13) passing.

## Compatibility notes

- No migrations (still 015, unchanged since v0.4.0); upgrading is a binary
  swap, and rollback is the previous binary.
- No API contract changes; the release is frontend-only.
- Behavior change is confined to the go-live validation flow: a
  wider-grant scenario now ends with two explicit notices and a 10/11
  readiness (retry available) instead of a silent abort; the nominal
  403 path is unchanged.

## Verification

- Frontend tests 263/263 (new cases: `classifyRuntimeValidationRun` treats
  an unexpected deny probe as a diagnosis, not an abort, across all four
  outcomes; `envHealthCheck` threads per-target classified probe failures
  into the unreachable detail); `make check`, `make release-check`, and
  `make evaluation-readiness` green on the tagged tree.
- PR CI 6/6 on #411; main CI green on merge commit a0d3e10.
- Browser end-to-end on the preview stack: a real wider-grant scenario
  (an Export grant chain on the Knowledge MCP target) produced both notices
  in Simplified Chinese and English — capability named, observed HTTP 200
  versus expected 403, recovery guidance — with the allowed call recorded,
  readiness at 10/11, retry available, and zero console warnings; the
  cockpit modal rendered the full `UPSTREAM_CONNECT_ERROR` dial detail.

## Known follow-ups (not blocking)

- The grant chain (tenant entitlement → workspace assignment → instance
  assignment) has no DELETE endpoint, so a wider-grant scenario cannot be
  cleaned up from the console — surfaced by #41 triage; separate backend
  work item.
- Finding #6: handoff view/copy audit events still pending a dedicated pass.
- Demo identity semantics (per-holder views, the #16 family) remain a future
  work item.
