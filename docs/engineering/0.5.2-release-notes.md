# AgentHarbor v0.5.2 Release Notes

Status: released 2026-10-01. Patch release on top of v0.5.1: grant-chain
removal, end to end (issue #413) — the three DELETE endpoints on the
backend (PR #414) plus the console's per-layer management modal (PR #415).
No schema changes, no migrations; the API additions are purely additive.

## Highlights

- Grant-chain removal endpoints (issue #413, PR #414). `DELETE
  /api/v1/tenant-entitlements/{id}`, `DELETE /api/v1/workspace-assignments/{id}`,
  and `DELETE /api/v1/instance-assignments/{id}` map to a status transition
  (`enabled` → `disabled`) rather than row deletion: applied permission
  packages keep the row ids they recorded, the audit trail survives, and
  runtime decisions already skip disabled rows at every level. Parents
  refuse with `409 GRANT_CHAIN_CHILDREN_ACTIVE` while enabled children
  still reference them, so narrowing a grant wider than a package always
  proceeds leaves-first. Each removal emits a
  `tenant_entitlement.disabled` / `workspace_assignment.disabled` /
  `instance_assignment.disabled` audit event mirroring the created-event
  metadata (bilingual console labels included). This closes the gap
  surfaced by external evaluation round 6 (finding 41's triage): the
  v0.5.1 go-live notice's recovery guidance — "narrow the conflicting
  grants and re-run" — is now actionable through the product instead of
  dead-ending at a backend restart.
- Grant-chain management in the console (PR #415). The
  capability-governance grants card gains a per-chain 管理 / Manage action
  opening a three-layer chain-detail modal — tenant entitlement, workspace
  assignments, caller assignments — with per-layer status chips and
  disable buttons. The modal is fully derived from live data, so each
  layer flips to 已停用 / Disabled in place after a disable; a
  children-active refusal renders as explicit per-layer guidance (disable
  the enabled children first) in Simplified Chinese and English.

## Compatibility notes

- No migrations (still 015, unchanged since v0.4.0); upgrading is a binary
  swap, and rollback is the previous binary.
- API additions only: three new DELETE endpoints. No existing route,
  contract, or payload changed.
- Removal semantics are a status transition, not row deletion — lists keep
  showing disabled rows, and repeat DELETE is idempotent (200 with the
  disabled row).

- Browser verification of the console modal in Simplified Chinese and
  English: chain created through the UI, both 409 guidances rendered,
  leaf-first disabling through all three layers, zero console warnings.
