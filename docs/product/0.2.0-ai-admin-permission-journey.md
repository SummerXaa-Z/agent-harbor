# v0.2.0 AI Admin Permission Journey

AgentHarbor v0.2.0 focuses on making agent permission operations usable by non-technical administrators without weakening security controls.

The product direction is: an administrator can describe a permission need in plain language, choose a permission package template, preview the exact allow/deny outcome, apply the package through existing tenant/workspace/caller grants, and inspect evidence afterward.

## Primary Journey

**User:** tenant administrator, platform operator, or security reviewer.

**Scenario:** grant a sales assistant agent read-only CRM access for one tenant scope, while blocking contract export, finance fields, cross-region data, and privileged tools.

1. The administrator opens the **AI Admin** workspace.
2. They describe the intended access in natural language.
3. AgentHarbor maps the request to a permission package template, such as **Sales read-only**.
4. The workbench shows the selected tenant, workspace, caller instance, MCP target, region, and subject selector.
5. AgentHarbor drafts a permission change from discovered MCP capability metadata.
6. The draft separates allowed capabilities from blocked capabilities.
7. A pre-publish simulation shows expected `allow` and `deny` decisions before anything is applied.
8. A policy gate shows whether the package can be applied directly or requires approval first.
9. For direct-apply packages, the administrator confirms the package.
10. For approval-required packages, the administrator creates an approval request that snapshots the exact draft, template version, scope, allowed capabilities, data scopes, and policy-gate reasons.
11. A reviewer approves or rejects the pending request. Rejected requests cannot authorize apply.
12. AgentHarbor applies the direct package, or the approved matching package with `approvalRequestId`, through the existing capability approval, tenant entitlement, workspace assignment, and instance assignment APIs.
13. AgentHarbor records the package application with the template version, draft id, created entitlement and assignment ids, capability ids, and applied data scopes. When approval is used, the applied audit event links the approval request id.
14. The tenant access profile refreshes so the administrator can inspect the resulting grant chain and evidence.

## Permission Package Templates

The first slice ships deterministic templates rather than free-form policy generation. This keeps the flow explainable and testable.

Initial templates:

- **Sales read-only**: allows read capabilities and blocks export, delete, admin, high-risk, critical-risk, and restricted capabilities.
- **Support ticket triage**: allows read and bounded write capabilities while blocking destructive and privileged operations.
- **Analytics sandbox**: allows read and execute capabilities while blocking production writes, exports, and admin operations.
- **Audit read-only**: allows low-risk reads and requires separate approval for exports.

## AI-Friendly Control Boundary

The AI-friendly goal is not automatic production mutation. The safe flow is:

```text
natural-language request
  -> deterministic permission package draft
  -> pre-publish simulation
  -> administrator confirmation or approval request
  -> control-plane writes
  -> permission package application record
  -> tenant access-profile evidence
```

This means an admin agent can help understand, plan, simulate, and submit permission changes, but the platform still keeps confirmation, permission checks, and auditability in the control plane.

The first direct-apply envelope is intentionally narrow. Low-risk read-oriented packages can be applied directly after administrator confirmation. Drafts that include allowed write, export, delete, admin, high-risk, critical-risk, confidential, or restricted capabilities remain explainable and can move forward only after a matching approval request is approved.

## Current v0.2.0 Slice

The current implementation exposes deterministic permission package operations through the backend API, the web console, and a management MCP endpoint, while keeping the web console's local template logic as a development fallback. Successful package applications are persisted as structured application records in both the in-memory repository and PostgreSQL-backed repository, approval requests are persisted as structured review evidence, and the web console shows the latest matching approval request plus application evidence.

The AI Admin workspace now includes a live approval journey workbench for the approval-required **Support ticket triage** path. The browser run creates fresh `ui-approval-*` tenant, caller, and target identifiers, discovers `search_customer`, `update_ticket`, and `export_contracts`, creates and approves a matching approval request, applies with `approvalRequestId`, sends subject-scoped runtime MCP calls with `user:support-001`, and refreshes profile plus audit evidence.

The management API now supports:

- `GET /api/v1/permission-packages/templates`
- `POST /api/v1/permission-packages/drafts`
- `POST /api/v1/permission-packages/approval-requests`
- `GET /api/v1/permission-packages/approval-requests?tenantId=&workspaceId=&templateId=&targetId=&callerInstanceId=&status=&limit=`
- `POST /api/v1/permission-packages/approval-requests/{id}/approve`
- `POST /api/v1/permission-packages/approval-requests/{id}/reject`
- `POST /api/v1/permission-packages:apply`
- `GET /api/v1/permission-packages/applications?tenantId=&workspaceId=&templateId=&targetId=&callerInstanceId=&limit=`

The management MCP endpoint is available at `POST /api/v1/management/mcp` and `POST /api/v1/management/mcp/rpc`. It exposes these first admin-agent tools:

- `list_permission_package_templates`
- `draft_permission_package`
- `create_permission_package_approval_request`
- `list_permission_package_approval_requests`
- `approve_permission_package_approval_request`
- `reject_permission_package_approval_request`
- `apply_permission_package`
- `list_permission_package_applications`
- `explain_permission_package_draft`
- `explain_access_decision`
- `get_tenant_access_profile`
- `list_agents`
- `list_capabilities`

The explain tools are read-only. They help an admin agent tell a non-technical administrator why a permission package cannot be applied, why a capability is currently denied, which evidence layer is missing, and what the next remediation step should be.

Applying a direct-apply package writes the same objects the core journey already uses:

- capability approval
- tenant entitlement
- workspace assignment
- caller instance assignment
- data scopes
- approval request evidence when required
- permission package application record

This is intentionally conservative: it proves the user journey while keeping runtime enforcement on the existing production path. Approval-required drafts without a matching approved request do not create entitlements, assignments, application records, or applied audit events.

## Executable Journey Check

For product evaluation, run the browser journey:

```bash
make demo
```

Then open `http://127.0.0.1:5174/`, switch to **AI Admin**, and run **Live Approval Journey**. A complete run reaches `8/8` across tenant tree, caller/target registration, capability discovery, approved request, approved apply, runtime allow/deny, tenant access profile, and applied audit event evidence.

The repository includes a local scenario for the approval-required path:

```bash
AGENT_HARBOR_ALLOW_PRIVATE_UPSTREAMS=true make run
make scenario-permission-package-approval
```

The scenario creates a three-level tenant tree, registers a caller and mock MCP target, discovers `search_customer`, `update_ticket`, and `export_contracts`, drafts a **Support ticket triage** package, verifies the approval gate, creates and approves a matching approval request, applies with `approvalRequestId`, and then checks `tools/list`, allowed and denied MCP calls, tenant access-profile evidence, the permission package application list, and the applied audit event.
