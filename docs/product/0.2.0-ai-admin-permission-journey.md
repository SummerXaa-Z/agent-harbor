# v0.2.0 Permission Request Approval Journey

AgentHarbor v0.2.0 focuses on making agent permission operations usable by non-technical administrators without weakening security controls.

AgentHarbor v0.2.0 聚焦于让非技术管理员也能完成 Agent 权限运营，同时不削弱安全控制。

The product direction is: an administrator can describe a permission need in plain language, choose a permission package template, preview the exact allow/deny outcome, apply the package through existing tenant/workspace/caller grants, and inspect the resulting records afterward.

产品方向是：管理员可以用自然语言描述权限需求，选择权限包模板，预览精确的允许/拒绝结果，通过现有租户/工作区/调用方授权链落地权限，并在事后查看记录。

## Key Messages / 对外主张

- **Clear tenant boundaries / 租户边界清楚**: three-level tenants, workspaces, and caller instances jointly decide which data an agent can access. 三级租户、工作区和调用方实例共同决定 Agent 可访问的数据。
- **Controlled permission changes / 权限变更可控**: administrators use permission packages to request access, and risky capabilities require approval before they are applied. 管理员通过权限包发起申请，高风险能力先审批再落地。
- **Clear go-live status / 上线状态清楚**: runtime allow/deny traces, tenant access profiles, and audit events support go-live decisions. 运行时允许/拒绝追踪、租户访问画像和审计事件共同支撑上线验收。

## Positioning / 产品定位

AgentHarbor supports MCP gateway behavior, but v0.2.0 is not trying to compete as a generic MCP gateway. MCP tools are one governed capability type. The differentiating product surface is tenant-first permission operations: template-based change drafting, simulation, approval, transactional apply, data-scope enforcement, and acceptance review.

AgentHarbor 支持 MCP 网关行为，但 v0.2.0 不以通用 MCP Gateway 作为竞争目标。MCP 工具只是被治理的能力类型之一。真正的差异化产品界面是租户优先的权限运营：基于模板生成变更草案、模拟、审批、事务化落地、数据范围控制和验收复核。

## Primary Journey

**User:** tenant administrator, platform operator, or security reviewer.

**用户：**租户管理员、平台操作员或安全审核人。

**Scenario:** grant a support assistant agent tenant-scoped ticket read and bounded update access, while blocking contract export, ticket deletion, admin operations, cross-region data, and privileged tools.

**场景：**为客服助手 Agent 授予租户范围内的工单查询和有限更新权限，同时阻止合同导出、删除工单、管理操作、跨区域数据和高权限工具。

1. The administrator opens the **Permission Changes** workspace.
   管理员打开 **权限变更** 工作区。
2. They describe the intended access in natural language.
   管理员用自然语言描述预期访问需求。
3. AgentHarbor maps the request to a permission package template, such as **Support ticket triage**.
   AgentHarbor 将请求映射到权限包模板，例如 **Support ticket triage / 客服工单处理**。
4. The assistant shows the selected tenant, workspace, caller instance, MCP target, region, and access object such as a role, department, or member. The technical subject selector stays in Advanced settings.
   权限变更工作台展示选定的租户、工作区、调用方实例、MCP 目标、区域和访问对象，例如角色、部门或成员；技术主体选择器保留在高级设置中。
5. AgentHarbor drafts a permission change from discovered MCP capability metadata.
   AgentHarbor 根据已发现的 MCP 能力元数据生成权限变更草案。
6. The draft separates allowed capabilities from blocked capabilities.
   草案区分允许能力和阻止能力。
7. A pre-publish simulation shows expected `allow` and `deny` decisions before anything is applied.
   发布前模拟会在真正落地前展示预期的 `allow` 和 `deny` 决策。
8. A policy gate shows whether the package can be applied directly or requires approval first.
   策略门控展示该权限包可以直接应用，还是必须先审批。
9. AgentHarbor runs apply preflight before any write. Preflight checks draft readiness, policy gate, approval match, data-scope fit, planned grant objects, and existing grant chains without writing permissions or consuming approval.
   AgentHarbor 会在任何写入前运行应用前预检。预检会检查草案就绪、策略门禁、审批匹配、数据范围边界、计划授权对象和已有授权链，不会写入权限，也不会消费审批。
10. For direct-apply packages, the administrator confirms the package only after preflight is ready.
   对可直接应用的权限包，管理员只在预检就绪后确认应用。
11. For approval-required packages, the administrator creates an approval request that snapshots the exact draft, template version, scope, allowed capabilities, data scopes, and policy-gate reasons. Approval requests expire after 24 hours.
   对需要审批的权限包，管理员创建审批请求，快照记录精确草案、模板版本、作用域、允许能力、数据范围和策略门控原因。审批请求 24 小时后过期。
12. A configured reviewer approves or rejects the pending request from the review queue scoped to their tenant subtree and workspace. Rejected requests cannot authorize apply.
   已配置审批人从限定到其租户子树和工作区的审批队列中批准或拒绝待处理请求。被拒绝的请求不能授权应用。
13. AgentHarbor applies the direct package, or the approved matching package with `approvalRequestId`, through the existing capability approval, tenant entitlement, workspace assignment, and instance assignment APIs only when preflight has no blockers.
   AgentHarbor 仅在预检无阻断时，通过现有能力审批、租户授权、工作区分配和实例分配 API 应用直接权限包，或用 `approvalRequestId` 应用匹配的已批准权限包。
14. AgentHarbor records the package application with the template version, draft id, created entitlement and assignment ids, capability ids, and applied data scopes. When approval is used, the approval request is consumed in the same repository transaction or lock as that application and cannot be reused.
   AgentHarbor 记录权限包应用，包含模板版本、草案 ID、创建的授权和分配 ID、能力 ID 以及已应用的数据范围。使用审批时，审批请求会在与应用记录相同的仓库事务或锁内被消费，且不能复用。
15. The tenant access profile refreshes so the administrator can inspect the resulting grant chain and runtime records.
   租户访问画像刷新后，管理员可以检查最终授权链和记录。
16. The administrator reviews the application impact before any rollback planning: created objects, active or missing current state, capability manual-review rows, and read-only rollback review steps.
   管理员在规划任何回滚前复核应用影响：已创建对象、当前有效或缺失状态、能力人工评审项，以及只读回滚评审步骤。
17. The administrator can rehearse grant drift from the same panel. AgentHarbor returns simulated missing/inactive blockers and read-only remediation actions without mutating permission state.
   管理员可以在同一个面板演练授权漂移。AgentHarbor 会返回模拟的缺失/未启用阻断和只读处置动作，但不会修改权限状态。
18. Before claiming the package is production-ready, the administrator runs the read-only go-live readiness gate. It combines preflight, latest application, health, impact, tenant access profile, runtime allow/deny traces, and applied audit records into a final ready, needs-review, or blocked decision.
   在声明权限包生产可用前，管理员运行只读状态检查。状态检查会汇总预检、最新应用、落地状态、影响复核、租户访问画像、运行时允许/拒绝追踪和应用审计记录，给出最终可上线、需复核或阻断判断。
19. The administrator exports a bounded JSON acceptance report from the same readiness result for security handoff.
   管理员从同一份上线就绪结果导出有边界的 JSON 验收报告，用于安全交接。

## Permission Package Templates

The first slice ships deterministic templates rather than free-form policy generation. This keeps the flow explainable and testable.

首个切片提供确定性的模板，而不是自由生成策略。这样流程更可解释，也更可测试。

Initial templates:

- **Sales read-only / 销售只读**: allows read capabilities and blocks export, delete, admin, high-risk, critical-risk, and restricted capabilities. 允许读取能力，阻止导出、删除、管理、高风险、关键风险和受限能力。
- **Support ticket triage / 客服工单处理**: allows read and bounded write capabilities while blocking destructive and privileged operations. 允许读取和有限写入能力，同时阻止破坏性和高权限操作。
- **Analytics sandbox / 分析沙箱**: allows read and execute capabilities while blocking production writes, exports, and admin operations. 允许读取和执行能力，同时阻止生产写入、导出和管理操作。
- **Audit read-only / 审计只读**: allows low-risk reads and requires separate approval for exports. 允许低风险读取，导出需要单独审批。

## AI-Friendly Control Boundary

The AI-friendly goal is not automatic production mutation. The safe flow is:

AI 友好的目标不是自动修改生产权限。安全流程是：

```text
natural-language request
  -> deterministic permission package draft
  -> pre-publish simulation
  -> administrator confirmation or approval request
  -> read-only apply preflight
  -> control-plane writes
  -> permission package application record
  -> read-only application impact review
  -> read-only production readiness gate
  -> read-only production acceptance report
  -> tenant access-profile records
```

This means an admin agent can help understand, plan, simulate, and submit permission changes, but the platform still keeps confirmation, permission checks, and auditability in the control plane.

这意味着管理 Agent 可以帮助理解、规划、模拟和提交权限变更，但确认、权限检查和审计性仍保留在控制平面。

The first direct-apply envelope is intentionally narrow. Low-risk read-oriented packages can be applied directly after administrator confirmation. Drafts that include allowed write, export, delete, admin, high-risk, critical-risk, confidential, or restricted capabilities remain explainable and can move forward only after a matching approval request is approved.

首个直接应用范围会刻意保持狭窄。低风险、读取导向的权限包可在管理员确认后直接应用。包含允许写入、导出、删除、管理、高风险、关键风险、机密或受限能力的草案仍保持可解释，但只能在匹配的审批请求获批后继续。

## Current v0.2.0 Slice

The current implementation exposes deterministic permission package operations through the backend API, the web console, and a management MCP endpoint, while keeping the web console's local template logic as a development fallback. Successful package applications are persisted as structured application records in both the in-memory repository and PostgreSQL-backed repository, approval requests are persisted as structured review records, and the web console shows the latest matching approval request plus read-only apply preflight, application record, read-only application health, read-only application impact review, read-only production readiness, and a bounded production acceptance report. Apply preflight is exposed at `POST /api/v1/permission-packages:preflight` and as `preflight_permission_package` for admin agents; it returns blockers, warnings, planned changes, and existing grant-chain records without creating entitlements, assignments, application records, audit events, or consuming approval requests. Production readiness is exposed at `GET /api/v1/permission-packages/production-readiness` and as `check_permission_package_production_readiness`; it aggregates preflight, latest application, health, impact, access-profile, runtime, and audit records without mutating state. The production acceptance report is exposed at `GET /api/v1/permission-packages/production-readiness/report` and as `export_permission_package_production_report`; the older `export_permission_package_production_evidence` tool name remains available as a compatibility alias. Readiness and acceptance-report responses include stable `nextActionCode` values such as `apply_permission_package`, `run_denied_runtime_call`, and `export_production_evidence` so the web console and admin agents can localize the next safe action without parsing English `nextActions`. Permission package drafts and instance assignments require an explicit access-object subject selector and reject empty or bare `*` selectors. Approval requests include expiry, consumption metadata, and per-capability configuration fingerprints so expired, already-used, mismatched, or drifted approvals fail before writing permissions; approved apply writes capability updates, entitlements, assignments, the application record, approval consumption, and applied audit records through one repository transaction or memory-store lock. Deployments can configure `AGENT_HARBOR_ADMIN_IDENTITIES` to bind `requestedBy` and `reviewedBy` to authenticated admin keys, and `AGENT_HARBOR_APPROVAL_REVIEWERS` so REST, management MCP, and the Approval queue can filter approval queues by reviewer route; approve/reject operations reject self-approval and deny reviewers outside the configured tenant-subtree or workspace route. The web console also exposes read-only effective permission explanations backed by the same decision evaluator as runtime enforcement and management MCP.

当前实现通过后端 API、Web 控制台和 management MCP endpoint 暴露确定性的权限包操作，同时保留 Web 控制台本地模板逻辑作为开发兜底。成功应用的权限包会在内存仓库和 PostgreSQL 仓库中保存为结构化应用记录；审批请求会保存为结构化审查记录；Web 控制台会展示最新匹配的审批请求、只读应用前预检、应用记录、只读落地状态、只读影响复核、只读状态检查结果和有边界的上线验收报告。应用前预检通过 `POST /api/v1/permission-packages:preflight` 暴露，并作为 `preflight_permission_package` 提供给管理 Agent；它返回阻断项、风险提示、计划变更和已有授权链记录，但不会创建授权、分配、应用记录、审计事件，也不会消费审批请求。状态检查通过 `GET /api/v1/permission-packages/production-readiness` 暴露，并作为 `check_permission_package_production_readiness` 提供给管理 Agent；它汇总预检、最新应用、落地状态、影响复核、访问画像、运行时和审计记录，且不修改状态。上线验收报告通过 `GET /api/v1/permission-packages/production-readiness/report` 暴露，并作为 `export_permission_package_production_report` 提供给管理 Agent；旧工具名 `export_permission_package_production_evidence` 会继续作为兼容别名保留。状态检查结果和验收报告会返回稳定的 `nextActionCode`，例如 `apply_permission_package`、`run_denied_runtime_call` 和 `export_production_evidence`，让 Web 控制台和管理 Agent 不解析英文 `nextActions` 也能本地化下一步安全动作。权限包草案和实例授权必须绑定明确的访问对象主体选择器，并拒绝空值或裸 `*`。审批请求包含过期、消费元数据和每能力配置指纹，因此过期、已使用、不匹配或能力配置漂移的审批都会在写入权限前失败；已批准应用会通过一个仓库事务或内存锁写入能力更新、授权、分配、应用记录、审批消费和应用审计记录。部署可以配置 `AGENT_HARBOR_ADMIN_IDENTITIES` 将发起人和审批人绑定到已认证管理 key，并配置 `AGENT_HARBOR_APPROVAL_REVIEWERS` 让 REST、management MCP 和待审批请求按审批人路由过滤审批队列；批准/驳回会拒绝自审批，并在审批人超出已配置租户子树或工作区路由时拒绝操作。Web 控制台还提供只读权限判定说明，复用运行时 enforcement 和 management MCP 使用的同一套决策评估器。

Apply preflight distinguishes legacy grant-chain overlap from a completed permission change. A manually imported or legacy grant chain remains a warning so administrators can review overlap; a matching application record returns the blocking `application_already_applied` check so the console and admin agents stop duplicate apply attempts and direct the operator to status review instead.

应用前预检会区分历史授权链重叠和已经完成的权限变更。手工导入或历史遗留授权链仍然只是风险提示，方便管理员复核是否重叠；匹配到应用记录时会返回阻断项 `application_already_applied`，让控制台和管理 Agent 停止重复应用，并引导操作人查看当前落地状态。

Apply preflight also returns stable `nextActionCodes` such as `create_approval_request`, `apply_permission_package`, `narrow_data_scope`, and `review_current_application` next to the legacy human-readable `nextActions`. Web console copy and management agents should prefer the codes and only fall back to `nextActions` for older servers.

应用前预检还会在旧版可读 `nextActions` 旁返回稳定的 `nextActionCodes`，例如 `create_approval_request`、`apply_permission_package`、`narrow_data_scope` 和 `review_current_application`。Web 控制台文案和管理 Agent 应优先使用代码，仅在连接旧服务时回退到 `nextActions`。

Permission-package policy gates also expose `nextActionCodes` for approval-required drafts. Today the policy-gate code is `create_approval_request`, matching the preflight approval blocker, so admin agents can move from draft explanation to approval setup without parsing English text.

权限包策略门禁也会为需审批草案暴露 `nextActionCodes`。当前策略门禁代码为 `create_approval_request`，与预检里的审批阻断保持一致，因此管理 Agent 可以从草案解释直接进入审批配置，而不需要解析英文文案。

The web console's policy-gate presenter also reads these codes before falling back to reason keys, so approval-required prompts stay localized and do not leak backend natural-language `nextActions` into the operator path.

Web 控制台的策略门禁 presenter 也会先读取这些代码，再回退到原因 key，因此需审批提示会保持本地化，不会把后端自然语言 `nextActions` 暴露到操作路径里。

Management MCP `explain_permission_package_draft` also returns top-level `nextActionCodes` for the same draft explanation. Codes include `fix_draft_readiness`, `refresh_capabilities`, `narrow_data_scope`, `create_approval_request`, `review_blocked_simulation_rows`, and `apply_permission_package`, while legacy `nextActions` remain available for human-readable output.

Management MCP 的 `explain_permission_package_draft` 也会在同一份草案解释上返回顶层 `nextActionCodes`。代码包括 `fix_draft_readiness`、`refresh_capabilities`、`narrow_data_scope`、`create_approval_request`、`review_blocked_simulation_rows` 和 `apply_permission_package`；旧版 `nextActions` 继续保留，供人类阅读。

Management MCP `explain_access_decision` returns stable `nextActionCodes` for the same access decision explanation. Codes include `refresh_capabilities`, `approve_capability`, `use_permission_package`, `create_workspace_assignment`, `create_caller_assignment`, `narrow_data_scope`, `review_deny`, `inspect_access_profile`, and `no_change_required`. Admin agents should prefer the codes when deciding whether to open a permission-package flow, inspect the access profile, or stop because access is already allowed.

Management MCP 的 `explain_access_decision` 也会在同一份访问判定说明中返回稳定的 `nextActionCodes`。代码包括 `refresh_capabilities`、`approve_capability`、`use_permission_package`、`create_workspace_assignment`、`create_caller_assignment`、`narrow_data_scope`、`review_deny`、`inspect_access_profile` 和 `no_change_required`。管理 Agent 判断是否进入权限包流程、查看权限画像，或因为访问已经允许而停止时，应优先读取这些代码。

The Permission Changes workspace now presents the approval-required **Support ticket triage** path as a task-first production approval workspace. The first screen is no longer a product-message card or status-card dashboard; it opens directly into a focused workbench with current status and next action at the top, request information on the left, approval/apply/validation handling on the right, and acceptance details collapsed below. `POST /api/v1/permission-packages/workbench:preview` provides the read-only projection behind this workbench, so the UI does not expose draft, approval, application, preflight, health, impact, and readiness objects as peer cards. The current process step is exposed with `aria-current="step"` and localized process wording so operators can scan the flow without reading raw ids, and each process step is clickable so operators can jump back to configuration, permissions, approval, apply, or go-live readiness without manually hunting through the page. The design follows enterprise management workspace principles: keep the main surface quiet, make the primary action obvious, and move expert records into expandable acceptance details. The request form shows readable tenant hierarchy, workspace, caller, target service, access object, and permission template labels first; raw tenant, workspace, caller, and target ids plus technical subject selectors are folded into Advanced settings and acceptance details. The selected access object is still enforced by backend readiness and write APIs, so removing or changing it to an unbounded selector blocks approval and apply. Missing or pending approvals are shown as pending work, while production blockers are reserved for rejected approvals, failed runtime records, or failed readiness checks. A pending approval request can be withdrawn by its original requester before review; withdrawal removes it from the pending queue and does not roll back any already-applied permission application. Preflight, effective permission explanation, application health, impact review, approval queue, production readiness, and audit records remain available under **Acceptance Details** for security and operations users. The tenant access profile remains available from the dedicated Access workspace and as supporting records inside the permission change flow, rather than as a competing large card on the Permission Changes first screen. The **View access profile** exit carries the same tenant, workspace, caller, target, capability, and subject context into the Access workspace and shows readable business names before the profile API finishes loading. The browser run creates fresh `ui-approval-*` tenant, caller, and target identifiers, discovers `search_customer`, `update_ticket`, and `export_contracts`, creates and approves a matching approval request, applies with `approvalRequestId`, sends subject-scoped runtime MCP calls with `user:support-001`, and refreshes profile plus audit records. The Approval queue lets a security reviewer enter their approver identity, fetch pending approvals scoped to the current request, and approve or reject individual requests with the same backend route enforcement; production deployments can bind that reviewer identity to `X-Admin-Key` through `AGENT_HARBOR_ADMIN_IDENTITIES`. The explanation panel lets an operator inspect the current allow/deny outcome, decision layers, returned data scopes, and recommended next actions for a selected tenant, workspace, caller, target, and capability without mutating permissions. The health panel derives ready, drifted, and needs-review status from each application's impact calculation; it is a read-only inspection layer, not a scheduler, notification hook, or rollback executor. The impact panel resolves the recorded entitlement, workspace assignment, instance assignment, and capability ids against current state, shows created/active/missing counts, marks capabilities for manual review, and lists rollback review steps without mutating permissions. The go-live readiness panel is the final read-only operator gate for the primary journey. The console shows runtime checks for API reachability, Mock MCP reachability, subject-header CORS, local private-upstream mode, and live data source before it mutates permission state.

`tools/list` 还会为每个管理工具返回 `execution` 元数据，包括 `idempotency`（`safe_repeat`、`conditional_repeat` 或 `not_idempotent`）、`confirmationRequired`、可选的 `preflightTool`、可选的 `auditResourceType` 和可选的 `returnsSecret`。管理 Agent 执行写操作前应先读取这些元数据：不可幂等或要求确认的工具需要显式交给操作员确认；`apply_permission_package` 应先执行 `preflight_permission_package`；会返回一次性密钥的工具不能把密钥写入日志或持久记录。

For tools with `confirmationRequired: true`, the management MCP server enforces the handoff. Calls must include a top-level `confirmation` object inside `arguments`, for example `{"confirmation":{"confirmed":true,"reason":"Operator approved this permission change after reviewing the preflight result."}}`. Calls without `confirmation.confirmed=true` or a `confirmation.reason` between 1 and 500 characters fail before any state change. 对于 `confirmationRequired: true` 的工具，management MCP 服务端会强制校验确认信息。调用时必须在 `arguments` 中包含顶层 `confirmation` 对象，例如 `{"confirmation":{"confirmed":true,"reason":"管理员已查看预检结果并批准本次权限变更。"}}`。缺少 `confirmation.confirmed=true` 或长度不在 1 到 500 个字符之间的 `confirmation.reason` 会在写入任何状态之前失败。服务端也会把 `safety.mutatesState` 或 `safety.operationType="write"` 标记为写入的工具按需要确认处理，因此未来 execution 元数据漏配时也会拒绝未确认调用。
