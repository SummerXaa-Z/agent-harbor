# v0.2.0 Permission Package Approval Journey

AgentHarbor v0.2.0 focuses on making agent permission operations usable by non-technical administrators without weakening security controls.

AgentHarbor v0.2.0 聚焦于让非技术管理员也能完成 Agent 权限运营，同时不削弱安全控制。

The product direction is: an administrator can describe a permission need in plain language, choose a permission package template, preview the exact allow/deny outcome, apply the package through existing tenant/workspace/caller grants, and inspect evidence afterward.

产品方向是：管理员可以用自然语言描述权限需求，选择权限包模板，预览精确的允许/拒绝结果，通过现有租户/工作区/调用方授权链落地权限，并在事后查看证据。

## Key Messages / 对外主张

- **Clear tenant boundaries / 租户边界清楚**: three-level tenants, workspaces, and caller instances jointly decide which data an agent can access. 三级租户、工作区和调用方实例共同决定 Agent 可访问的数据。
- **Controlled permission changes / 权限变更可控**: administrators use permission packages to request access, and risky capabilities require approval before they are applied. 管理员通过权限包发起申请，高风险能力先审批再落地。
- **Complete go-live evidence / 上线证据完整**: runtime allow/deny traces, tenant access profiles, and audit events support production acceptance. 运行时允许/拒绝追踪、租户访问画像和审计事件共同支撑上线验收。

## Positioning / 产品定位

AgentHarbor supports MCP gateway behavior, but v0.2.0 is not trying to compete as a generic MCP gateway. MCP tools are one governed capability type. The differentiating product surface is tenant-first permission operations: template-based change drafting, simulation, approval, transactional apply, data-scope enforcement, and evidence review.

AgentHarbor 支持 MCP 网关行为，但 v0.2.0 不以通用 MCP Gateway 作为竞争目标。MCP 工具只是被治理的能力类型之一。真正的差异化产品界面是租户优先的权限运营：基于模板生成变更草案、模拟、审批、事务化落地、数据范围控制和证据复查。

## Primary Journey

**User:** tenant administrator, platform operator, or security reviewer.

**用户：**租户管理员、平台操作员或安全审查员。

**Scenario:** grant a support assistant agent tenant-scoped ticket read and bounded update access, while blocking contract export, ticket deletion, admin operations, cross-region data, and privileged tools.

**场景：**为客服助手 Agent 授予租户范围内的工单查询和有限更新权限，同时阻止合同导出、删除工单、管理操作、跨区域数据和高权限工具。

1. The administrator opens the **Permission Packages** workspace.
   管理员打开 **权限包** 工作区。
2. They describe the intended access in natural language.
   管理员用自然语言描述预期访问需求。
3. AgentHarbor maps the request to a permission package template, such as **Support ticket triage**.
   AgentHarbor 将请求映射到权限包模板，例如 **Support ticket triage / 客服工单处理**。
4. The workbench shows the selected tenant, workspace, caller instance, MCP target, region, and subject selector.
   权限包审批台展示选定的租户、工作区、调用方实例、MCP 目标、区域和主体选择器。
5. AgentHarbor drafts a permission change from discovered MCP capability metadata.
   AgentHarbor 根据已发现的 MCP 能力元数据生成权限变更草案。
6. The draft separates allowed capabilities from blocked capabilities.
   草案区分允许能力和阻止能力。
7. A pre-publish simulation shows expected `allow` and `deny` decisions before anything is applied.
   发布前模拟会在真正落地前展示预期的 `allow` 和 `deny` 决策。
8. A policy gate shows whether the package can be applied directly or requires approval first.
   策略门控展示该权限包可以直接应用，还是必须先审批。
9. AgentHarbor runs apply preflight before any write. Preflight checks draft readiness, policy gate, approval match, data-scope fit, planned grant objects, and existing grant chains without writing permissions or consuming approval.
   AgentHarbor 会在任何写入前运行应用前预检。预检会检查草案就绪、策略门禁、审批匹配、数据范围边界、计划授权对象和已有授权链，不会写入权限，也不会消费审批。
10. For direct-apply packages, the administrator confirms the package only after preflight is ready.
   对可直接应用的权限包，管理员只在预检就绪后确认应用。
11. For approval-required packages, the administrator creates an approval request that snapshots the exact draft, template version, scope, allowed capabilities, data scopes, and policy-gate reasons. Approval requests expire after 24 hours.
   对需要审批的权限包，管理员创建审批请求，快照记录精确草案、模板版本、作用域、允许能力、数据范围和策略门控原因。审批请求 24 小时后过期。
12. A configured reviewer approves or rejects the pending request from the review queue scoped to their tenant subtree and workspace. Rejected requests cannot authorize apply.
   已配置审查员从限定到其租户子树和工作区的审批队列中批准或拒绝待处理请求。被拒绝的请求不能授权应用。
13. AgentHarbor applies the direct package, or the approved matching package with `approvalRequestId`, through the existing capability approval, tenant entitlement, workspace assignment, and instance assignment APIs only when preflight has no blockers.
   AgentHarbor 仅在预检无阻断时，通过现有能力审批、租户授权、工作区分配和实例分配 API 应用直接权限包，或用 `approvalRequestId` 应用匹配的已批准权限包。
14. AgentHarbor records the package application with the template version, draft id, created entitlement and assignment ids, capability ids, and applied data scopes. When approval is used, the approval request is consumed in the same repository transaction or lock as that application and cannot be reused.
   AgentHarbor 记录权限包应用，包含模板版本、草案 ID、创建的授权和分配 ID、能力 ID 以及已应用的数据范围。使用审批时，审批请求会在与应用记录相同的仓库事务或锁内被消费，且不能复用。
15. The tenant access profile refreshes so the administrator can inspect the resulting grant chain and evidence.
   租户访问画像刷新后，管理员可以检查最终授权链和证据。
16. The administrator reviews the application impact before any rollback planning: created objects, active or missing current state, capability manual-review rows, and read-only rollback review steps.
   管理员在规划任何回滚前复核应用影响：已创建对象、当前有效或缺失状态、能力人工评审项，以及只读回滚评审步骤。
17. The administrator can rehearse grant drift from the same panel. AgentHarbor returns simulated missing/inactive blockers and read-only remediation actions without mutating permission state.
   管理员可以在同一个面板演练授权漂移。AgentHarbor 会返回模拟的缺失/未启用阻断和只读处置动作，但不会修改权限状态。
18. Before claiming the package is production-ready, the administrator runs the read-only production readiness gate. It combines preflight, latest application, health, impact, tenant access profile, runtime allow/deny traces, and applied audit evidence into a final ready, needs-review, or blocked decision.
   在声明权限包生产可用前，管理员运行只读上线验收门禁。门禁会汇总预检、最新应用、落地状态、影响复核、租户访问画像、运行时允许/拒绝追踪和应用审计证据，给出最终可上线、需复核或阻断判断。
19. The administrator exports a bounded JSON evidence report from the same readiness result for security handoff.
   管理员从同一份上线验收结果导出有边界的 JSON 证据报告，用于安全交接。

## Permission Package Templates

The first slice ships deterministic templates rather than free-form policy generation. This keeps the flow explainable and testable.

首个切片提供确定性的模板，而不是自由生成策略。这样流程更可解释，也更可测试。

Initial templates:

- **Sales read-only / 销售只读**: allows read capabilities and blocks export, delete, admin, high-risk, critical-risk, and restricted capabilities. 允许读取能力，阻止导出、删除、管理、高风险、关键风险和受限能力。
- **Support ticket triage / 客服工单处理**: allows read and bounded write capabilities while blocking destructive and privileged operations. 允许读取和有限写入能力，同时阻止破坏性和高权限操作。
- **Analytics sandbox / 分析沙箱**: allows read and execute capabilities while blocking production writes, exports, and admin operations. 允许读取和执行能力，同时阻止生产写入、导出和管理操作。
- **Audit read-only / 审计只读**: allows low-risk reads and requires separate approval for exports. 允许低风险读取，导出需要单独审批。

## AI-Friendly Control Boundary

The AI-friendly goal is not automatic production mutation. The safe flow is:

AI 友好的目标不是自动修改生产权限。安全流程是：

```text
natural-language request
  -> deterministic permission package draft
  -> pre-publish simulation
  -> administrator confirmation or approval request
  -> read-only apply preflight
  -> control-plane writes
  -> permission package application record
  -> read-only application impact review
  -> read-only production readiness gate
  -> read-only production evidence report
  -> tenant access-profile evidence
```

This means an admin agent can help understand, plan, simulate, and submit permission changes, but the platform still keeps confirmation, permission checks, and auditability in the control plane.

这意味着管理 Agent 可以帮助理解、规划、模拟和提交权限变更，但确认、权限检查和审计性仍保留在控制平面。

The first direct-apply envelope is intentionally narrow. Low-risk read-oriented packages can be applied directly after administrator confirmation. Drafts that include allowed write, export, delete, admin, high-risk, critical-risk, confidential, or restricted capabilities remain explainable and can move forward only after a matching approval request is approved.

首个直接应用范围会刻意保持狭窄。低风险、读取导向的权限包可在管理员确认后直接应用。包含允许写入、导出、删除、管理、高风险、关键风险、机密或受限能力的草案仍保持可解释，但只能在匹配的审批请求获批后继续。

## Current v0.2.0 Slice

The current implementation exposes deterministic permission package operations through the backend API, the web console, and a management MCP endpoint, while keeping the web console's local template logic as a development fallback. Successful package applications are persisted as structured application records in both the in-memory repository and PostgreSQL-backed repository, approval requests are persisted as structured review evidence, and the web console shows the latest matching approval request plus read-only apply preflight, application evidence, read-only application health, read-only application impact review, read-only production readiness, and a bounded production evidence report. Apply preflight is exposed at `POST /api/v1/permission-packages:preflight` and as `preflight_permission_package` for admin agents; it returns blockers, warnings, planned changes, and existing grant-chain evidence without creating entitlements, assignments, application records, audit events, or consuming approval requests. Production readiness is exposed at `GET /api/v1/permission-packages/production-readiness` and as `check_permission_package_production_readiness`; it aggregates preflight, latest application, health, impact, access-profile, runtime, and audit evidence without mutating state. The production evidence report is exposed at `GET /api/v1/permission-packages/production-readiness/report` and as `export_permission_package_production_evidence`; it projects the same decision into bounded JSON evidence references for handoff. Approval requests include expiry and consumption metadata so expired or already-used approvals fail before writing permissions; approved apply writes capability updates, entitlements, assignments, the application record, approval consumption, and applied audit evidence through one repository transaction or memory-store lock. Deployments can configure `AGENT_HARBOR_APPROVAL_REVIEWERS` so REST, management MCP, and the Permission Packages Reviewer queue can filter approval queues by reviewer; approve/reject operations are denied when the reviewer is outside the configured tenant-subtree or workspace route. The web console also exposes read-only effective permission explanations backed by the same decision evaluator as runtime enforcement and management MCP.

当前实现通过后端 API、Web 控制台和 management MCP endpoint 暴露确定性的权限包操作，同时保留 Web 控制台本地模板逻辑作为开发兜底。成功应用的权限包会在内存仓库和 PostgreSQL 仓库中保存为结构化应用记录；审批请求会保存为结构化审查证据；Web 控制台会展示最新匹配的审批请求、只读应用前预检、应用证据、只读落地状态、只读影响复核、只读上线验收和有边界的上线证据报告。应用前预检通过 `POST /api/v1/permission-packages:preflight` 暴露，并作为 `preflight_permission_package` 提供给管理 Agent；它返回阻断项、风险提示、计划变更和已有授权链证据，但不会创建授权、分配、应用记录、审计事件，也不会消费审批请求。上线验收通过 `GET /api/v1/permission-packages/production-readiness` 暴露，并作为 `check_permission_package_production_readiness` 提供给管理 Agent；它汇总预检、最新应用、落地状态、影响复核、访问画像、运行时和审计证据，且不修改状态。上线证据报告通过 `GET /api/v1/permission-packages/production-readiness/report` 暴露，并作为 `export_permission_package_production_evidence` 提供给管理 Agent；它把同一份判断投影为有边界的 JSON 证据引用，便于交接。审批请求包含过期和消费元数据，因此过期或已使用的审批会在写入权限前失败；已批准应用会通过一个仓库事务或内存锁写入能力更新、授权、分配、应用记录、审批消费和应用审计证据。部署可以配置 `AGENT_HARBOR_APPROVAL_REVIEWERS`，让 REST、management MCP 和 权限包审查员队列按审查员过滤审批队列，并在审查员超出已配置租户子树或工作区路由时拒绝批准/驳回操作。Web 控制台还提供只读权限判定说明，复用运行时 enforcement 和 management MCP 使用的同一套决策评估器。

The Permission Packages workspace now presents the approval-required **Support ticket triage** path as a production approval and acceptance console, with a top five-step go-live status rail, a Reviewer queue for routed approval work, an effective permission explanation panel, an application health panel, an application impact review panel, and a production readiness panel. The page keeps the first screen focused on one operator path: product message, start-approval CTA, status rail, and one primary action. Missing or pending approvals are shown as pending work, while production blockers are reserved for rejected approvals, failed runtime evidence, or failed readiness checks. The go-live rail rolls change request, approval, permission application, runtime verification, and production readiness into one operator decision before exposing detailed acceptance evidence and permission configuration in collapsed sections. The tenant access profile remains available from the dedicated Access workspace and as evidence inside the permission package flow, rather than as a competing large card on the Permission Packages first screen. The browser run creates fresh `ui-approval-*` tenant, caller, and target identifiers, discovers `search_customer`, `update_ticket`, and `export_contracts`, creates and approves a matching approval request, applies with `approvalRequestId`, sends subject-scoped runtime MCP calls with `user:support-001`, and refreshes profile plus audit evidence. The Reviewer queue lets a security reviewer enter their reviewer identity, fetch pending approvals scoped to the current package, and approve or reject individual requests with the same backend route enforcement. The explanation panel lets an operator inspect the current allow/deny outcome, evidence layers, returned data scopes, and recommended next actions for a selected tenant, workspace, caller, target, and capability without mutating permissions. The health panel derives ready, drifted, and needs-review status from each application's impact calculation; it is a read-only inspection layer, not a scheduler, notification hook, or rollback executor. The impact panel resolves the recorded entitlement, workspace assignment, instance assignment, and capability ids against current state, shows created/active/missing counts, marks capabilities for manual review, and lists rollback review steps without mutating permissions. The production readiness panel is the final read-only operator gate for the primary journey. The console shows runtime checks for API reachability, Mock MCP reachability, subject-header CORS, local private-upstream mode, and live data source before it mutates permission state.

权限包工作区现在把需要审批的 **Support ticket triage / 客服工单处理** 路径呈现为生产审批与验收控制台，顶部包含五步上线状态轨、用于路由审批工作的审查员队列、权限判定说明面板、落地状态面板、影响复核面板和上线验收面板。页面首屏只聚焦一条操作路径：产品主张、发起审批入口、状态轨和一个主操作。未发起或待处理审批会显示为待处理事项；只有审批被拒、运行证据失败或上线验收失败才会呈现为生产阻断。上线状态轨把变更申请、审批、权限落地、运行验证和上线验收合并为一个操作员决策，再把详细验收证据和权限配置收敛到折叠区。租户访问画像仍可从独立的权限工作区进入，并作为权限包流程内证据保留，而不是在权限包首屏作为并列的大卡片抢占注意力。

The current release posture is production-hardening first. The repository includes a safety baseline gate that starts the API with `AGENT_HARBOR_ADMIN_KEY` configured and private upstreams disabled, then verifies management API authorization, permission-package authorization, management MCP authorization, default loopback/private upstream rejection, and public HTTPS MCP target registration.

当前发布姿态是生产加固优先。仓库包含安全基线门禁：启动配置了 `AGENT_HARBOR_ADMIN_KEY` 且禁用私网上游的 API，然后验证管理 API 授权、权限包授权、management MCP 授权、默认拒绝 loopback/私网上游，以及公共 HTTPS MCP 目标可注册。

`list_permission_package_approval_requests` accepts optional reviewer routing. Approve and reject tools validate the same reviewer scope before changing status. The preflight, production readiness, and explain tools are read-only. They help an admin agent tell a non-technical administrator why a permission package cannot be applied, whether it is production-ready, why a capability is currently denied, which evidence layer is missing, and what the next remediation step should be.

`list_permission_package_approval_requests` 支持可选的审查员路由。批准和驳回工具在变更状态前会校验同一套审查员范围。预检、上线验收和判定说明类工具为只读工具，帮助管理 Agent 向非技术管理员说明权限包为什么不能应用、是否生产可用、能力当前为什么被拒绝、缺少哪一层证据，以及下一步修复动作是什么。

Applying a direct-apply package writes the same objects the core journey already uses:

- capability approval
- tenant entitlement
- workspace assignment
- caller instance assignment
- data scopes
- read-only apply preflight evidence
- approval request evidence when required
- permission package application record
- read-only application health summary
- read-only application impact review
- read-only application remediation plan
- read-only production readiness gate
- read-only drift rehearsal

This is intentionally conservative: it proves the user journey while keeping runtime enforcement on the existing production path. Approval-required drafts without a matching approved, unexpired, unconsumed request do not create entitlements, assignments, application records, or applied audit events; preflight reports those blockers before apply and remains read-only.

The application impact response includes `remediationPlan.executionMode="read_only"` with ordered actions for capability manual review, drift investigation, grant disablement from instance to workspace to tenant, and final effective-permission verification. It does not execute rollback.

影响复核响应包含 `remediationPlan.executionMode="read_only"`，并按顺序给出能力人工评审、漂移调查、从实例到工作区再到租户的授权禁用、以及最终有效权限校验动作。该计划不执行回滚。

When recorded grants are missing, no longer enabled, or no allowed capability ids are recorded, both `rollbackReview` and `remediationPlan` include stable `blockerCodes` so the console and admin agents can explain unsafe states without parsing English text.

当已记录授权缺失、不再启用，或应用记录没有允许能力 ID 时，`rollbackReview` 和 `remediationPlan` 都会包含稳定的 `blockerCodes`，控制台和管理 Agent 可以不解析英文文本就解释不安全状态。

The same endpoint accepts `rehearsal=grant_drift` to compute the real impact first, copy the response, and simulate one missing workspace assignment plus one inactive instance assignment when available. The response includes `rehearsal.enabled=true` and `rehearsal.scenario="grant_drift"` so operators and admin agents can label it clearly. A subsequent impact request without `rehearsal` returns the real grant state.

同一端点支持 `rehearsal=grant_drift`：先计算真实影响，再复制响应，并在有对象时模拟一个缺失的工作区分配和一个未启用的实例分配。响应包含 `rehearsal.enabled=true` 和 `rehearsal.scenario="grant_drift"`，便于操作员和管理 Agent 明确标记这是演练结果。之后不带 `rehearsal` 的影响请求仍返回真实授权状态。

## Executable Journey Check

For product evaluation, run the browser journey:

```bash
make demo
```

Then open `http://127.0.0.1:5174/`, switch to **Permission Packages**, click **Run acceptance**, confirm **Go-Live Status** reaches ready, confirm the application health panel shows a healthy row, confirm **Production Readiness** reports ready, export the production evidence JSON, click that row's **Review impact** action, and optionally click **Rehearse drift**.
