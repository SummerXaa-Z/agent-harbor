# v0.2.0 AI Admin Permission Journey

AgentHarbor v0.2.0 focuses on making agent permission operations usable by non-technical administrators without weakening security controls.

AgentHarbor v0.2.0 聚焦于让非技术管理员也能完成 Agent 权限运营，同时不削弱安全控制。

The product direction is: an administrator can describe a permission need in plain language, choose a permission package template, preview the exact allow/deny outcome, apply the package through existing tenant/workspace/caller grants, and inspect evidence afterward.

产品方向是：管理员可以用自然语言描述权限需求，选择权限包模板，预览精确的允许/拒绝结果，通过现有租户/工作区/调用方授权链落地权限，并在事后查看证据。

## Positioning / 产品定位

AgentHarbor supports MCP gateway behavior, but v0.2.0 is not trying to compete as a generic MCP gateway. MCP tools are one governed capability type. The differentiating product surface is tenant-first permission operations: template-based change drafting, simulation, approval, transactional apply, data-scope enforcement, and evidence review.

AgentHarbor 支持 MCP 网关行为，但 v0.2.0 不以通用 MCP Gateway 作为竞争目标。MCP 工具只是被治理的能力类型之一。真正的差异化产品界面是租户优先的权限运营：基于模板生成变更草案、模拟、审批、事务化落地、数据范围控制和证据复查。

## Primary Journey

**User:** tenant administrator, platform operator, or security reviewer.

**用户：**租户管理员、平台操作员或安全审查员。

**Scenario:** grant a sales assistant agent read-only CRM access for one tenant scope, while blocking contract export, finance fields, cross-region data, and privileged tools.

**场景：**为销售助手 Agent 授予单一租户范围内的 CRM 只读访问，同时阻止合同导出、财务字段、跨区域数据和高权限工具。

1. The administrator opens the **AI Admin** workspace.
   管理员打开 **AI Admin** 工作区。
2. They describe the intended access in natural language.
   管理员用自然语言描述预期访问需求。
3. AgentHarbor maps the request to a permission package template, such as **Sales read-only**.
   AgentHarbor 将请求映射到权限包模板，例如 **Sales read-only**。
4. The workbench shows the selected tenant, workspace, caller instance, MCP target, region, and subject selector.
   工作台展示选定的租户、工作区、调用方实例、MCP 目标、区域和主体选择器。
5. AgentHarbor drafts a permission change from discovered MCP capability metadata.
   AgentHarbor 根据已发现的 MCP 能力元数据生成权限变更草案。
6. The draft separates allowed capabilities from blocked capabilities.
   草案区分允许能力和阻止能力。
7. A pre-publish simulation shows expected `allow` and `deny` decisions before anything is applied.
   发布前模拟会在真正落地前展示预期的 `allow` 和 `deny` 决策。
8. A policy gate shows whether the package can be applied directly or requires approval first.
   策略门控展示该权限包可以直接应用，还是必须先审批。
9. For direct-apply packages, the administrator confirms the package.
   对可直接应用的权限包，管理员进行确认。
10. For approval-required packages, the administrator creates an approval request that snapshots the exact draft, template version, scope, allowed capabilities, data scopes, and policy-gate reasons. Approval requests expire after 24 hours.
   对需要审批的权限包，管理员创建审批请求，快照记录精确草案、模板版本、作用域、允许能力、数据范围和策略门控原因。审批请求 24 小时后过期。
11. A configured reviewer approves or rejects the pending request from the review queue scoped to their tenant subtree and workspace. Rejected requests cannot authorize apply.
   已配置审查员从限定到其租户子树和工作区的审批队列中批准或拒绝待处理请求。被拒绝的请求不能授权应用。
12. AgentHarbor applies the direct package, or the approved matching package with `approvalRequestId`, through the existing capability approval, tenant entitlement, workspace assignment, and instance assignment APIs.
   AgentHarbor 通过现有能力审批、租户授权、工作区分配和实例分配 API 应用直接权限包，或用 `approvalRequestId` 应用匹配的已批准权限包。
13. AgentHarbor records the package application with the template version, draft id, created entitlement and assignment ids, capability ids, and applied data scopes. When approval is used, the approval request is consumed in the same repository transaction or lock as that application and cannot be reused.
   AgentHarbor 记录权限包应用，包含模板版本、草案 ID、创建的授权和分配 ID、能力 ID 以及已应用的数据范围。使用审批时，审批请求会在与应用记录相同的仓库事务或锁内被消费，且不能复用。
14. The tenant access profile refreshes so the administrator can inspect the resulting grant chain and evidence.
   租户访问画像刷新后，管理员可以检查最终授权链和证据。
15. The administrator reviews the application impact before any rollback planning: created objects, active or missing current state, capability manual-review rows, and read-only rollback review steps.
   管理员在规划任何回滚前复盘应用影响：已创建对象、当前有效或缺失状态、能力人工评审项，以及只读回滚评审步骤。

## Permission Package Templates

The first slice ships deterministic templates rather than free-form policy generation. This keeps the flow explainable and testable.

首个切片提供确定性的模板，而不是自由生成策略。这样流程更可解释，也更可测试。

Initial templates:

- **Sales read-only / 销售只读**: allows read capabilities and blocks export, delete, admin, high-risk, critical-risk, and restricted capabilities. 允许读取能力，阻止导出、删除、管理、高风险、关键风险和受限能力。
- **Support ticket triage / 客服工单处理**: allows read and bounded write capabilities while blocking destructive and privileged operations. 允许读取和有限写入能力，同时阻止破坏性和高权限操作。
- **Analytics sandbox / 分析沙箱**: allows read and execute capabilities while blocking production writes, exports, and admin operations. 允许读取和执行能力，同时阻止生产写入、导出和管理操作。
- **Audit read-only / 审计只读**: allows low-risk reads and requires separate approval for exports. 允许低风险读取，导出需要单独审批。

## AI-Friendly Control Boundary

The AI-friendly goal is not automatic production mutation. The safe flow is:

AI 友好的目标不是自动修改生产权限。安全流程是：

```text
natural-language request
  -> deterministic permission package draft
  -> pre-publish simulation
  -> administrator confirmation or approval request
  -> control-plane writes
  -> permission package application record
  -> read-only application impact review
  -> tenant access-profile evidence
```

This means an admin agent can help understand, plan, simulate, and submit permission changes, but the platform still keeps confirmation, permission checks, and auditability in the control plane.

这意味着管理 Agent 可以帮助理解、规划、模拟和提交权限变更，但确认、权限检查和审计性仍保留在控制平面。

The first direct-apply envelope is intentionally narrow. Low-risk read-oriented packages can be applied directly after administrator confirmation. Drafts that include allowed write, export, delete, admin, high-risk, critical-risk, confidential, or restricted capabilities remain explainable and can move forward only after a matching approval request is approved.

首个直接应用范围会刻意保持狭窄。低风险、读取导向的权限包可在管理员确认后直接应用。包含允许写入、导出、删除、管理、高风险、关键风险、机密或受限能力的草案仍保持可解释，但只能在匹配的审批请求获批后继续。

## Current v0.2.0 Slice

The current implementation exposes deterministic permission package operations through the backend API, the web console, and a management MCP endpoint, while keeping the web console's local template logic as a development fallback. Successful package applications are persisted as structured application records in both the in-memory repository and PostgreSQL-backed repository, approval requests are persisted as structured review evidence, and the web console shows the latest matching approval request plus application evidence and read-only application impact review. Approval requests include expiry and consumption metadata so expired or already-used approvals fail before writing permissions; approved apply writes capability updates, entitlements, assignments, the application record, approval consumption, and applied audit evidence through one repository transaction or memory-store lock. Deployments can configure `AGENT_HARBOR_APPROVAL_REVIEWERS` so REST, management MCP, and the AI Admin Reviewer queue can filter approval queues by reviewer; approve/reject operations are denied when the reviewer is outside the configured tenant-subtree or workspace route. The web console also exposes read-only effective permission explanations backed by the same decision evaluator as runtime enforcement and management MCP.

当前实现通过后端 API、Web 控制台和 management MCP endpoint 暴露确定性的权限包操作，同时保留 Web 控制台本地模板逻辑作为开发兜底。成功应用的权限包会在内存仓库和 PostgreSQL 仓库中保存为结构化应用记录；审批请求会保存为结构化审查证据；Web 控制台会展示最新匹配的审批请求、应用证据和只读应用影响复盘。审批请求包含过期和消费元数据，因此过期或已使用的审批会在写入权限前失败；已批准应用会通过一个仓库事务或内存锁写入能力更新、授权、分配、应用记录、审批消费和应用审计证据。部署可以配置 `AGENT_HARBOR_APPROVAL_REVIEWERS`，让 REST、management MCP 和 AI Admin 审查员队列按审查员过滤审批队列，并在审查员超出已配置租户子树或工作区路由时拒绝批准/驳回操作。Web 控制台还提供只读有效权限解释，复用运行时 enforcement 和 management MCP 使用的同一套决策评估器。

The AI Admin workspace now includes a live approval journey workbench for the approval-required **Support ticket triage** path, a Reviewer queue for routed approval work, an effective permission explanation panel, and an application impact review panel. The browser run creates fresh `ui-approval-*` tenant, caller, and target identifiers, discovers `search_customer`, `update_ticket`, and `export_contracts`, creates and approves a matching approval request, applies with `approvalRequestId`, sends subject-scoped runtime MCP calls with `user:support-001`, and refreshes profile plus audit evidence. The Reviewer queue lets a security reviewer enter their reviewer identity, fetch pending approvals scoped to the current package, and approve or reject individual requests with the same backend route enforcement. The explanation panel lets an operator inspect the current allow/deny outcome, evidence layers, returned data scopes, and recommended next actions for a selected tenant, workspace, caller, target, and capability without mutating permissions. The impact panel resolves the recorded entitlement, workspace assignment, instance assignment, and capability ids against current state, shows created/active/missing counts, marks capabilities for manual review, and lists rollback review steps without mutating permissions. The workbench shows first-run readiness for API reachability, Mock MCP reachability, subject-header CORS, local private-upstream mode, and live data source before it mutates permission state.

AI Admin 工作区现在包含一个实时审批旅程工作台，用于需要审批的 **Support ticket triage** 路径，并提供面向审查员的路由审批队列、有效权限解释面板和应用影响复盘面板。浏览器运行会创建新的 `ui-approval-*` 租户、调用方和目标标识符，发现 `search_customer`、`update_ticket` 和 `export_contracts`，创建并批准匹配的审批请求，使用 `approvalRequestId` 应用权限包，携带 `user:support-001` 发送主体范围运行时 MCP 调用，并刷新画像和审计证据。审查员队列允许安全审查员输入自己的审查员标识，获取限定到当前权限包范围的待处理审批，并在同一套后端路由校验下逐条批准或驳回。解释面板允许操作员在不修改权限的前提下，查看选定租户、工作区、调用方、目标和能力当前的允许/拒绝结果、证据层、返回的数据范围和建议下一步动作。影响复盘面板会把记录中的租户授权、工作区分配、实例分配和能力 ID 与当前状态对齐，展示已创建/有效/缺失数量，将能力标为人工评审，并列出不执行变更的回滚评审步骤。工作台会在修改权限状态前展示 API 可达性、Mock MCP 可达性、主体 header CORS、本地私网上游模式和实时数据源的首跑就绪状态。

The current release posture is production-hardening first. The repository includes a safety baseline gate that starts the API with `AGENT_HARBOR_ADMIN_KEY` configured and private upstreams disabled, then verifies management API authorization, permission-package authorization, management MCP authorization, default loopback/private upstream rejection, and public HTTPS MCP target registration.

当前发布姿态是生产加固优先。仓库包含安全基线门禁：启动配置了 `AGENT_HARBOR_ADMIN_KEY` 且禁用私网上游的 API，然后验证管理 API 授权、权限包授权、management MCP 授权、默认拒绝 loopback/私网上游，以及公共 HTTPS MCP 目标可注册。

The management API now supports:

- `GET /api/v1/permission-packages/templates`
- `POST /api/v1/permission-packages/drafts`
- `POST /api/v1/permission-packages/approval-requests`
- `GET /api/v1/permission-packages/approval-requests?tenantId=&workspaceId=&templateId=&targetId=&callerInstanceId=&status=&reviewer=&limit=`
- `POST /api/v1/permission-packages/approval-requests/{id}/approve`
- `POST /api/v1/permission-packages/approval-requests/{id}/reject`
- `POST /api/v1/permission-packages:apply`
- `GET /api/v1/permission-packages/applications?tenantId=&workspaceId=&templateId=&targetId=&callerInstanceId=&limit=`
- `GET /api/v1/permission-packages/applications/{id}/impact?tenantId=&workspaceId=`
- `GET /api/v1/access-decisions:explain?tenantId=&workspaceId=&callerInstanceId=&targetId=&capabilityId=&subjectId=`

The management MCP endpoint is available at `POST /api/v1/management/mcp` and `POST /api/v1/management/mcp/rpc`. It exposes these first admin-agent tools:

- `list_permission_package_templates`
- `draft_permission_package`
- `create_permission_package_approval_request`
- `list_permission_package_approval_requests`
- `approve_permission_package_approval_request`
- `reject_permission_package_approval_request`
- `apply_permission_package`
- `list_permission_package_applications`
- `explain_permission_package_draft`
- `explain_access_decision`
- `get_tenant_access_profile`
- `list_agents`
- `list_capabilities`

`list_permission_package_approval_requests` accepts optional reviewer routing. Approve and reject tools validate the same reviewer scope before changing status. The explain tools are read-only. They help an admin agent tell a non-technical administrator why a permission package cannot be applied, why a capability is currently denied, which evidence layer is missing, and what the next remediation step should be.

`list_permission_package_approval_requests` 支持可选的审查员路由。批准和驳回工具在变更状态前会校验同一套审查员范围。解释类工具为只读工具，帮助管理 Agent 向非技术管理员说明权限包为什么不能应用、能力当前为什么被拒绝、缺少哪一层证据，以及下一步修复动作是什么。

Applying a direct-apply package writes the same objects the core journey already uses:

- capability approval
- tenant entitlement
- workspace assignment
- caller instance assignment
- data scopes
- approval request evidence when required
- permission package application record
- read-only application impact review

This is intentionally conservative: it proves the user journey while keeping runtime enforcement on the existing production path. Approval-required drafts without a matching approved, unexpired, unconsumed request do not create entitlements, assignments, application records, or applied audit events.

## Executable Journey Check

For product evaluation, run the browser journey:

```bash
make demo
```

Then open `http://127.0.0.1:5174/`, switch to **AI Admin**, run **Live Approval Journey**, and click **Review impact** in the application evidence panel. A complete run reaches `8/8` across tenant tree, caller/target registration, capability discovery, approved request, approved apply, runtime allow/deny, tenant access profile, and applied audit event evidence; the impact review then shows the created grant objects, capability manual-review row, and rollback review steps.

For a release-candidate browser gate, run:

```bash
make ai-admin-browser-journey
```

This starts the same local browser stack, verifies browser subject-header CORS, and runs the approval-required package scenario against the live services.

For a production-default safety gate, run:

```bash
make production-hardening
```

This gate is included in `make release-check` and should pass before any production-readiness or release-candidate claim.

The repository includes a local scenario for the approval-required path:

```bash
AGENT_HARBOR_ALLOW_PRIVATE_UPSTREAMS=true make run
make scenario-permission-package-approval
```

The scenario creates a three-level tenant tree, registers a caller and mock MCP target, discovers `search_customer`, `update_ticket`, and `export_contracts`, drafts a **Support ticket triage** package, verifies the approval gate, creates and approves a matching approval request, applies with `approvalRequestId`, verifies the request is consumed and cannot be reused, and then checks `tools/list`, allowed and denied MCP calls, tenant access-profile evidence, the permission package application list, the read-only application impact endpoint, and the applied audit event.
