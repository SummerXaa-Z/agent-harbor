# v0.3.0 Access Handoff PRD

> 状态: Draft, 已综合 2026-06-10 手写脑暴、v0.2.0 现状差距分析和平台化愿景草案。
> 范围: 本文档定义可执行的 v0.3.0 MVP。更大的多资源权限包、模型预算、授权 TTL、回滚执行和完整自助门户放入 `0.3.0-permission-platform-requirements.md` 作为 0.3+ 平台愿景。

## 一句话定位

AgentHarbor v0.3.0 要把“管理员已经完成权限变更”延伸成“被授权用户可以安全开始使用”。核心不是再做一个 MCP Gateway, 而是在现有权限包、审批、预检、应用和上线验收闭环之后，交付一张可复制、可审计、可过期的接入卡片。

## 背景

当前 v0.2.0 已经证明了管理员权限运营闭环:

- 管理员选择租户、工作区、调用方、目标服务、访问对象和权限包模板。
- 系统生成确定性权限包草案，区分允许能力和阻止能力。
- 高风险能力必须审批，预检在写入前阻断不安全状态。
- 应用后记录授权对象、应用记录、审计、运行时允许/拒绝记录和上线就绪结果。
- Management MCP 可以让管理 Agent 起草、预检、审批、应用和解释权限。

手写脑暴提出的下一层问题是: 权限包审批通过以后，普通用户和集成者如何知道自己被授权了什么，怎么拿到 Token, 怎么复制接入配置，怎么用模型或 Agent 能力开始工作。现在项目有短期 Agent Key 能力，但它仍是管理端对象；也有权限包应用记录，但它更偏审计记录，不是面向被授权用户的接入交付物。

这说明 v0.3.0 不应该继续只加管理员审计面板。它要补的是“领取方”体验: 普通用户、集成开发者和团队负责人能看见可用资源、理解边界、复制正确配置，并在控制平面保留审批、确认和审计。

## 产品设计目标

1. **承接新技术**: MCP 生态扩张后，企业内 Agent、工具、数据库、模型和 skill 资产都会变成可开通资源。v0.3.0 先不实现全部资源类型，但 UI 和 API 语言不能把权限包永久锁死为 MCP 工具包。
2. **打开新市场**: 安全和平台团队买的是“管住、可审计、可回收”；业务团队和团队 Lead 买的是“快速开通、清楚可用、少排队”。v0.3.0 需要让第二类买家看到价值。
3. **满足新需求**: 权限运营从防御性治理扩展到供给性开通。审批、应用、记录仍在同一条控制链内，但交付物从审计记录变成可使用的接入说明。
4. **易用性优先**: 消费侧从零开始设计，标准是普通员工和集成开发者不用读源码，也能在几分钟内知道能用什么、怎么接入、什么不能做。

## 目标

### 产品目标

1. 让被授权用户能看到自己当前可用的权限包、能力清单、数据范围和有效期。
2. 让管理员在权限包应用成功后，可以把一份明确的接入说明交给用户或业务系统。
3. 让用户可以在不扩大权限的前提下申请或领取短期 Token, 复制 MCP 客户端配置和提示词模板。
4. 让安全审核人可以追踪“谁交付了什么接入信息、谁创建了 Token、Token 对应哪个权限包和数据范围”。
5. 为后续多资源权限包打基础: MCP tool、OpenAPI、数据库、skill bundle、Agent 能力、模型访问都应能成为被治理资源。

### 非目标

1. v0.3.0 不做完整 IAM 或企业 SSO 登录系统。用户身份先复用现有 subject selector 和 caller instance 边界。
2. v0.3.0 不允许普通用户自助扩大权限。任何新能力、新数据范围、新模型访问仍必须回到权限包申请和审批。
3. v0.3.0 不把 AgentHarbor 定位成模型网关或 MCP 市场。模型和 skill 只是被治理资源类型。
4. v0.3.0 不实现长期 API Key。接入 Token 继续短期、一次展示、可撤销。
5. v0.3.0 不执行自动回滚。已有只读影响复核和处置计划仍是安全边界。

## 核心概念

### Access Handoff / 接入交付

权限包成功应用后生成的只读交付视图。它不是新的授权源，而是现有权限包应用、访问画像、运行记录和 Agent Key 能力的组合投影。

接入交付包含:

- 权限包名称、版本、状态和审批记录。
- 租户、工作区、调用方、访问对象和 subject selector。
- 允许能力、阻止能力、数据范围、敏感等级和风险说明。
- 当前上线就绪状态和下一步动作。
- 可复制的 MCP 客户端配置片段。
- 可复制的提示词模板。
- 短期 Token 申请入口和一次性显示结果。
- 审计引用: application id、approval request id、audit event id、trace id。

### My Access / 我的权限

面向被授权用户的视图。v0.3.0 可以先做管理员控制台内的只读区域；后续再演进为独立用户门户。

### Multi-resource Permission Package / 多资源权限包

权限包未来不只包含 MCP capability。它应能表达:

- MCP 工具能力。
- OpenAPI endpoint 能力。
- 数据库、数据湖、数据仓库的数据范围。
- Agent 自身能力，例如可调用哪些下游 Agent。
- skill bundle, 例如某类业务技能集合。
- model access, 例如可用模型、上下文长度、数据留存策略、成本预算。

v0.3.0 不实现完整多资源模型，但 PRD 要保留扩展方向，避免 UI 和 API 文案把权限包永久锁死为 MCP tool 包。

## MVP 用户旅程

### 旅程 1: 管理员完成权限变更后交付接入

1. 管理员在 Permission Changes 工作区完成审批、应用、运行验证和上线就绪检查。
2. 系统显示 **接入交付 / Access Handoff** 区域。
3. 管理员确认交付对象、权限包、允许能力、数据范围和 Token TTL。
4. 管理员复制接入说明，或创建一次性短期 Token。
5. 系统记录 `access_handoff.viewed`、`access_token.created` 或 `access_handoff.copied` 审计事件。

成功标准:

- 管理员无需理解底层 entitlements 和 assignments, 也能把“怎么用”交给用户。
- 页面不展示 secret 历史值；Token 只在创建后显示一次。
- 接入说明明确写出权限边界和数据范围，不暗示拥有未授权能力。

### 旅程 2: 被授权用户查看自己能用什么

1. 用户进入 My Access 或管理员分享的交付页。
2. 系统根据 subject/caller/tenant/workspace 展示当前有效权限包。
3. 用户看到可用能力、不可用能力、数据范围、有效期和安全提示。
4. 用户复制 MCP 配置或提示词模板。
5. 如果需要 Token, 用户发起短期 Token 请求或联系管理员领取；v0.3.0 可以先由管理员确认创建。

成功标准:

- 用户能在 1 分钟内回答“我能访问什么”和“我不能访问什么”。
- 用户复制的配置不会绕过 AgentHarbor 运行时。
- 如果权限未 ready, 页面展示原因和下一步，而不是给出可用配置。

### 旅程 3: 安全审核接入交付记录

1. 安全审核人查看某次权限包应用。
2. 系统展示该应用关联的交付记录和 Token 记录。
3. 审核人可以看到 Token 前缀、创建人、过期时间、绑定 caller、subject、权限包、数据范围。
4. 审核人可以撤销 Token 或要求重新审批权限包。

成功标准:

- 审核人不需要读取运行日志全文就能定位接入来源。
- 审计记录不包含明文 Token、上游凭据、完整 Authorization header。

## 功能需求

### FR-1 接入交付只读投影

系统应提供一个只读投影，按权限包应用范围返回接入交付信息。

输入:

- tenantId
- workspaceId
- callerInstanceId
- targetId
- templateId
- subjectId 或 subjectSelector
- applicationId 可选

输出:

- handoff status: `ready`、`needs_review`、`blocked`
- permission package template and version
- latest application summary
- approval record summary
- allowed capabilities and blocked capabilities
- effective data scopes
- production readiness summary
- copyable MCP config
- copyable prompt template
- token eligibility: whether a short-lived Token can be created
- next action code

约束:

- blocked 状态不得返回可直接使用的 Token 创建动作。
- 如果缺少 access object 或 subject selector, 返回 blocker。
- 所有文案必须支持中文和英文。

### FR-2 接入交付卡片

Web 控制台应在权限包应用成功后展示 **接入交付** 卡片。

卡片信息层级:

1. 当前是否可交付。
2. 交付给谁: 租户、工作区、调用方、访问对象。
3. 可以用什么: 权限包、允许能力、数据范围。
4. 怎么接入: MCP config、提示词模板、短期 Token。
5. 谁来负责: 申请人、审批人、交付人、审计引用。

交互:

- 复制 MCP config。
- 复制提示词模板。
- 创建短期 Token。
- 撤销已创建 Token。
- 展开高级记录。

### FR-3 短期 Token 申请与创建

系统应复用现有 Agent Key 安全约束，但把入口语义从“管理员创建 key”升级为“为已授权接入创建短期 Token”。

要求:

- Token 只可绑定 active local caller。
- TTL 默认 30 分钟，最大 1 小时。
- Token 创建前必须检查 handoff status 是 ready。
- Token 只显示一次。
- Token 记录必须包含 permission package application reference。
- 撤销 Token 后立即无法通过 Bearer token 访问运行时。

v0.3.0 可以先由管理员创建 Token；后续 My Access 版本再支持用户自助申请和审批。

### FR-4 可复制 MCP 配置

系统应生成可复制配置片段，帮助用户把 AgentHarbor 接入本地 Agent 或 MCP 客户端。

配置必须包含:

- AgentHarbor runtime endpoint。
- Authorization header 占位符。
- subject id/header 示例。
- target/capability 说明。
- 数据范围说明。
- 有效期和撤销提示。

配置不得包含:

- 明文上游凭据。
- 已过期 Token。
- 管理员 API key。
- 与当前权限包无关的 capability。

### FR-5 可复制提示词模板

系统应生成一段面向最终用户或 Agent builder 的提示词模板。

模板应说明:

- 当前 Agent 可以调用哪些能力。
- 必须遵守哪些数据范围。
- 遇到被拒绝能力时应该如何解释。
- 不得尝试绕过 AgentHarbor 或请求管理员凭据。

示例结构:

```text
你可以通过 AgentHarbor 使用以下已授权能力: ...
数据范围限制: ...
如果操作被拒绝, 请说明缺少的权限层级, 不要要求用户提供管理员密钥。
```

### FR-6 Management MCP 扩展

Management MCP 后续应增加接入交付相关只读工具，让管理 Agent 能完成解释和交付。

建议工具:

- `get_access_handoff`
- `explain_access_handoff`
- `create_access_handoff_token`
- `revoke_access_handoff_token`

约束:

- `get_access_handoff` 和 `explain_access_handoff` 只读。
- Token 创建工具必须要求 handoff ready, 并记录审计。
- MCP 工具返回 structuredContent, 文本字段保持摘要化。

### FR-7 多资源权限包预留

v0.3.0 文案和数据结构不应把权限包称为“只包含 MCP 工具”。可以继续优先实现 MCP tool, 但模型命名应兼容后续资源类型。

建议资源类型:

- `mcp_capability`
- `openapi_operation`
- `data_asset`
- `agent_capability`
- `skill_bundle`
- `model_access`

v0.3.0 不要求全部落库，但 PRD、导航和 UI 文案应避免和未来扩展冲突。

## UI 需求

### Permission Changes 增量

在现有权限变更工作台中增加 **接入交付** 区块:

- 位于应用成功和上线就绪之后。
- 默认展示交付摘要和主要复制动作。
- 高级记录折叠，避免挤压主流程。
- 当 readiness blocked 时，显示缺口，不显示 Token 创建按钮。

### My Access 后续入口

后续新增 `My Access / 我的权限` 导航:

- 当前权限包。
- 可用能力。
- 数据范围。
- Token 请求。
- 接入说明。
- 最近运行拒绝原因。

v0.3.0 可以先不加独立导航，只在管理员视角完成接入交付闭环。

## 安全和合规要求

1. 明文 Token 只显示一次。
2. 审计、trace、docs、scenario output 不得包含明文 Token、cookie、Authorization header 或上游凭据。
3. Token 创建必须绑定明确 caller 和 subject selector。
4. 空 subject selector 或裸 `*` 不得进入接入交付 ready 状态。
5. 用户不能通过 Access Handoff 申请超过当前权限包的数据范围。
6. 模型访问和 skill bundle 后续进入权限包时，必须有单独风险级别和审批原因。
7. 复制提示词必须明确“不能绕过 AgentHarbor 或索要管理员密钥”。

## 指标

产品指标:

- 权限包应用成功后，接入交付 ready 率。
- 用户从看到交付卡片到复制配置的时间。
- Token 创建成功率和撤销率。
- 因权限不清导致的重复审批请求数量。
- 运行时 denied trace 中“误用未授权能力”的比例。

质量指标:

- 接入交付投影测试覆盖 ready、blocked、needs_review。
- Token 一次性展示和密钥泄漏测试通过。
- 中文和英文主路径文案完整。
- `make check` 和权限包主旅程继续通过。

## 分阶段计划

### Phase 1: Access Handoff MVP

- 新增接入交付只读投影。
- Web 控制台展示接入交付卡片。
- 复制 MCP config 和提示词模板。
- 管理员从交付卡片创建短期 Token。
- 审计记录交付查看、复制和 Token 创建。

### Phase 2: My Access 自助视图

- 增加面向被授权用户的只读权限页。
- 用户可以查看自己的权限包和数据范围。
- 用户提交 Token 申请，由管理员或策略批准。
- 用户能看到最近 denied 原因和下一步申请建议。

### Phase 3: 多资源权限包

- 把资源类型扩展到 OpenAPI、数据系统、Agent 能力、skill bundle、model access。
- 权限包模板从 action-only 进化为 resource-type aware。
- 策略门禁按模型、数据、技能、成本预算生成审批原因。

### Phase 4: 企业化

- 身份源集成。
- 策略化审批人组。
- 审计系统和 SIEM 集成。
- 按团队或企业 SKU 提供配额、保留期和治理报表。

## 验收标准

MVP 完成时，应该能演示:

1. 管理员完成 Support ticket triage 权限包审批和应用。
2. 权限包上线就绪后，页面出现 Access Handoff 卡片。
3. 卡片显示被授权对象、允许能力、阻止能力、数据范围和审计引用。
4. 卡片可以复制 MCP config 和提示词模板。
5. 管理员创建短期 Token, 明文只显示一次。
6. Token 可以用于已授权运行调用，不能用于未授权能力。
7. 撤销 Token 后运行调用失败。
8. 审计日志能查到接入交付和 Token 创建记录，且不包含明文 secret。

## 开放问题和推荐答案

1. **是否先做普通用户登录?**
   推荐不做。先用管理员视角交付卡片证明价值，避免把 v0.3.0 拖进 IAM 项目。

2. **Token 是用户自助创建还是管理员创建?**
   v0.3.0 推荐管理员创建，Phase 2 再做用户申请。原因是当前项目已有管理端 Agent Key 能力，风险最小。

3. **模型接入是否进入 MVP?**
   不进入 MVP, 但 PRD 保留 `model_access` 资源类型。模型权限会引入成本、数据留存、供应商合规，应该单独设计。

4. **skill bundle 是否进入 MVP?**
   不进入 MVP。先在权限包文案中避免 MCP-only 绑定，后续多资源权限包再实现。

5. **接入交付是持久对象还是只读投影?**
   MVP 推荐只读投影 + 审计事件。等 My Access 独立门户出现后，再决定是否持久化 handoff record。

## 结论

v0.2.0 解决的是“权限怎么安全变更”。v0.3.0 应解决“权限变更完成后怎么安全交付使用”。这正好承接脑暴里的权限包、Token、模型接入、管理员可用性和目标用户/定价思考，同时保持实现切片足够小: 先做 Access Handoff, 再做 My Access, 最后扩展到多资源权限包。
