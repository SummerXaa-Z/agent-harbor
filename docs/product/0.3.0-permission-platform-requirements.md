# AgentHarbor 0.3+ Permission Platform Vision

> 状态: Vision Draft, 用于承接 2026-06-10 产品脑暴和 v0.3.0 Access Handoff PRD 之外的平台化方向。
> 范围: 本文档不是 v0.3.0 MVP 执行清单。v0.3.0 的可执行需求以 `docs/product/0.3.0-access-handoff-prd.md` 为准。
> 语言: 草案阶段中文优先；进入公开评审或合入主文档前，按仓库惯例补齐中英双语。

## 1. 背景

v0.2.0 已经把管理员侧的权限变更审批旅程做深: 模板化草案、模拟、预检、审批、事务化应用、落地状态、影响复核、上线就绪门禁和报告导出。这条线的深度是够的。

宽度还不够，主要体现在两个方向:

1. **被治理的资源类型仍以 MCP 工具能力为中心。** Skill、数据库、Agent 服务、模型额度还没有进入统一权限包表达。
2. **产品重心仍在管理员视角。** 权限发放方有完整体验，但领取方和集成者还缺少“我能用什么、怎么接入、如何拿到短期 Token”的可用路径。

因此平台愿景是: 从租户优先权限治理工具，演进为企业 AI 资源开通与治理平台。权限包仍是统一载体，但它未来描述的是一组可被授予、可审批、可交付、可审计、可回收的 AI 资源。

## 2. 与 v0.3.0 PRD 的关系

| 文档 | 作用 | 范围 |
| --- | --- | --- |
| `0.3.0-access-handoff-prd.md` | 可执行 PRD | 权限应用成功后的接入交付卡片、可复制配置、提示词模板、管理员创建短期 Token、审计引用 |
| 本文档 | 平台愿景 | My Access 自助门户、登录/身份映射、多资源权限包、模型预算、授权 TTL、回滚执行、企业化能力 |

v0.3.0 先做 Access Handoff, 不是因为消费门户、模型预算或多资源权限包不重要，而是因为这些能力依赖身份、授权模型和运行时 enforcement 的更大改造。先补“接入交付”可以在不破坏 v0.2.0 安全边界的前提下证明业务价值。

## 3. 产品设计目标

- **新技术**: MCP 生态扩张，企业内 Agent、工具、数据库、模型和 skill 资产都会变成可治理资源。
- **新市场**: 买单角色从安全/平台团队扩展到业务团队。业务团队买的不是“管住”，而是“快速开通且不会越权”。
- **新需求**: 权限运营从防御性治理扩展到供给性开通。发现、申请、接入、配额、回收都应共用同一条授权链和审计链路。
- **易用性**: 管理侧已落地 task-first 工作台；消费侧标准是普通员工和集成者不读源码、不看授权链，也能快速接入已开放资源。

## 4. Persona

| | 平台 / 安全管理员 | 租户管理员 / 团队 Lead | 普通用户 / Agent 使用者 |
| --- | --- | --- | --- |
| 技术能力 | 高。熟悉 IAM、审计、网络边界 | 中。懂业务工具，不一定懂 MCP 协议和权限模型 | 低-中。会用 Claude / Cursor / 内部 Agent, 不懂租户/能力/授权链 |
| 核心痛点 | Agent 乱接工具无审计；权限发出去收不回来；出事时缺少清晰审计链 | 给团队开权限要排期；开完不知道实际开了什么、有没有越权 | 不知道公司开放了什么 AI 资源；申请 Token 流程长；接入配置看不懂 |
| 目标 | 全部访问有审批、有审计、可回收、可巡检 | 一次申请给团队开通一组资源，并能安全交付给成员 | 看到对自己开放的资源，复制配置，拿到短期 Token, 跑通第一次调用 |
| 当前覆盖 | v0.2.0 大部分覆盖，缺真实回收和生命周期 | v0.2.0 已覆盖权限变更主旅程，v0.3.0 补交付 | v0.2.0 基本未覆盖，v0.3+ 主战场 |

## 6. 商业化输入

目标决策人的层级决定定价范围。当前功能主要服务安全和平台团队；补齐消费侧和模型预算后，才能形成面向业务团队的第二条价值线。

| 决策人层级 | 买的是什么 | 对应能力 | 产品分层建议 |
| --- | --- | --- | --- |
| 开源社区 / 集成开发者 | 治理引擎本体和本地验证 | 租户树、授权链、运行时 enforcement、trace、短期 Agent Key | 开源核心 / Developer |
| 团队 Lead / 业务负责人 | 效率、自助、可预算 | My Access、接入配置复制、自助 Token、模型预算 | Team Governance |
| CISO / 平台负责人 / 合规负责人 | 审计、合规、可回收 | 审批路由、身份源集成、授权生命周期、多资源权限包、审计集成 | Enterprise Control Plane |

此节只作为产品分层依据，定价、商业版边界和 license 策略另行决策。

## 7. 平台能力方向

### R1 多资源权限包

未来权限包不应只描述 MCP capability。它应能包含:

- `mcp_capability`: 当前主路径。
- `openapi_operation`: OpenAPI endpoint 能力。
- `data_asset`: 数据库、数据湖、数据仓库的数据范围。
- `agent_capability`: 被治理的 Agent 服务能力，例如 PPT 生成、知识问答、审批处理。
- `skill_bundle`: 一组版本化 skill / prompt 资产。
- `model_access`: 模型、上下文长度、数据留存策略、成本预算。

关键约束:

- 不急于把所有资源压进同一个规则结构。模型预算、数据库行级范围、skill 版本指纹和 MCP action/risk/sensitivity 的约束不同。
- 第一个非 MCP 验证建议选择 `skill_bundle` 或 `openapi_operation`, 避免一开始就碰数据库行级权限和模型预算。
- 新资源类型必须继续进入预检、审批、应用记录、访问画像、health、impact、readiness 和报告导出。

### R2 My Access 自助消费侧

My Access 是被授权用户视角，不是管理员工作台的简化版。

目标能力:

- 登录后查看对自己开放的权限包。
- 查看可用能力、不可用能力、数据范围、有效期和安全提示。
- 复制 MCP config、system prompt、命令行接入片段。
- 发起短期 Token 申请。
- 查看最近 denied 原因和下一步申请建议。
- 退订或请求回收自己的接入。

分期建议:

1. v0.3.0: 只做管理员侧 Access Handoff, 不引入登录。
2. 0.3.x: 做 My Access 只读视图，身份先用轻量本地身份或由管理员指定 subject。
3. 后续: 引入 OIDC / IdP, 将登录身份稳定映射到 subjectId。

### R3 自助 Token 与凭据交付

现有 Agent Key 是短期、一次展示、可撤销的正确基础，但它现在是管理 API 能力。平台愿景是把它包装为“接入 Token”。

原则:

- Token 只能绑定明确 caller、subject、权限包应用和数据范围。
- Token 只显示一次，不能出现在 audit、trace、docs、scenario output 中。
- 自动签发必须依赖登录和 subject 映射。在这之前，v0.3.0 只允许管理员从 Access Handoff 创建。
- 高风险权限包不能因为“用户自助”绕过审批。

### R4 模型接入与预算

模型接入不是简单新增 target type。它引入第三个 enforcement 维度: 成本/额度。

目标能力:

- 模型 provider 作为被治理目标。
- 在 tenant / workspace / subject 层定义调用次数、token 量或金额上限。
- 超额时拒绝或降级到低成本模型。
- 模型调用写入 runtime metrics 和 trace。
- 提额走权限包审批链。

关键风险:

- 高并发扣减需要事务或预扣减设计，不能只靠事后 trace 汇总。
- 模型供应商凭据、数据留存策略和输出审计需要单独安全设计。
- 预算不应复用 `dataScopes`; 它是独立 enforcement 维度。

### R5 授权生命周期

v0.2.0 有审批请求过期和只读 impact review, 但授权本身还没有生命周期管理。

目标能力:

- 授权 TTL: entitlement / assignment 支持有效期，运行时到期即拒绝。
- 续期: 到期前提示，续期走审批链。
- 回收执行: 按只读 remediation plan 的顺序执行真实回收。
- 回收审批: 回收也是权限变更，需有审计和确认。
- Health 扩展: `expired`、`revoked`、`rollback_failed` 等状态。

关键约束:

- 回收执行不能作为 Access Handoff 的附带功能进入 v0.3.0。
- 到期拒绝必须在运行时判定生效，不能依赖后台任务先扫描。

## 8. 推荐路线

| 阶段 | 主题 | 内容 | 进入条件 |
| --- | --- | --- | --- |
| v0.3.0 | Access Handoff | 交付卡片、复制配置、提示词模板、管理员创建短期 Token、审计引用 | v0.2.0 权限变更主旅程稳定 |
| 0.3.x | My Access | 被授权用户只读视图、权限包列表、接入说明、Token 申请入口 | Access Handoff 证明交付价值 |
| 0.4.0 | 授权生命周期 | TTL、续期、真实回收、回收审计 | health / impact / readiness 对生命周期状态有稳定语义 |
| 0.5.0 | 模型接入与预算 | model provider、配额、计量、提额审批 | 身份映射和运行时计量可靠 |
| 0.6.0 | 多资源权限包 | skill bundle / OpenAPI / data asset / agent capability | 权限包核心接口能承载多资源 projection |
| Enterprise | 企业控制平面 | IdP、审批人组、SIEM、长期留存、治理报表 | 商业边界和部署模型清晰 |

每个阶段仍沿用现有工程纪律: scenario 脚本、`make check`、`make production-hardening`、核心权限包旅程和安全回归通过后，再推进下一阶段。

## 9. 成功指标

短期指标:

- 权限包应用成功后，Access Handoff ready 率。
- 从管理员看到交付卡片到复制配置的时间。
- Token 创建、撤销和运行时验证成功率。
- 因接入说明不清导致的重复审批请求数量下降。

中期指标:

- 普通用户从进入 My Access 到首次成功调用的时间小于 5 分钟。
- 自助 Token 申请 100% 走审批链并留存记录。
- 带 TTL 授权到期后运行时拒绝率 100%, health 识别率 100%。
- 至少 1 个非 MCP 资源类型走通完整审计链路。

长期指标:

- 模型预算不超卖。
- 回收执行后访问画像中残留授权对象为 0。
- 企业审计导出可直接支撑安全评审和合规交接。

## 10. 开放问题

1. **Agent 双重身份**: Agent 既是 caller 又是 target 时，是拆出 `agent_service` target, 还是让同一 Agent 实体挂双角色?
2. **subjectId 映射**: 当前 subject 是自由字符串。引入登录后，历史 trace 和授权里的字符串 subject 如何迁移或共存?
3. **Token 自动签发**: 低风险包是否允许自动签发，还是所有自助 Token 都要审批或管理员确认?
4. **预算一致性**: 高并发模型调用下，配额扣减采用同步事务、预扣减还是异步结算?
5. **接入片段凭据安全**: 短期 Token 默认 TTL、刷新方式、是否绑定客户端指纹?
6. **退订语义**: 用户退订只回收自己的 instance assignment, 还是也影响 subject 级可见性和 trace 查询?
7. **多资源模板抽象**: action/risk/sensitivity 是否足以覆盖 skill、模型和数据库，还是需要 resource-type-specific policy blocks?
