# 0.3.x 控制台消息本地化立项（Console Message Localization）

> 状态: Phase 1/2/3 已实施（2026-09-19，见下），立项收口。输入为 [0.3.x 豆包控制台评估](0.3.x-doubao-console-eval.md) 第二轮发现 #12A（系统性本地化缺口）与 #16（访问判定链中英混杂），以及已合并的文案轮 PR #378。
> 范围: 定义"后端产生的消息在中文控制台里的呈现契约"。工程级设计（code 清单、参数结构、护栏测试形态）开工前按仓库惯例补 `docs/engineering/0.3.x-*-design.md`。
> 语言: 立项阶段中文优先；进入公开评审前按仓库惯例补齐中英双语。

## 一句话定位

把"控制台里所有会直接读给管理员看的后端消息"从**英文原文直出**改为**稳定 code + 参数 → 前端 i18n 映射**，中文界面不再出现整句英文；API 面向 curl/AI 消费者的英文诊断语义保持不变。

## 问题与证据

豆包评估第二轮 #12A（原文摘录）：

> 上线检查页头部翻为「已阻断 这次权限变更暂不能上线。」，但紧随的主阻断原因是**未翻译的英文原句** "One or more applied capabilities changed after this permission package was applied."……排查确认后端就绪/预检消息全部为硬编码英文……等数十条，会原样进入中文界面，属**系统性本地化缺口**而非个例。

同轮 #16：访问查询判定链节点（"Caller Instance"、"matched"、"Caller instance … matches tenant … and workspace …."）与中文节点名混排。

这不是文案漏翻，而是**契约缺口**：前端 i18n（`frontend/src/i18n.ts`，zh/en 双语齐全）没有覆盖这类消息的机制，因为消息是后端拼好的整句，前端只能原样渲染。

## 方案选择

**A（推荐）code-first 契约：后端稳定 code + 参数，前端映射，英文 message 作为兜底与 API 语义保留。**

- 后端：就绪检查已带 code，零改动起步；仅当某条消息内嵌动态值且中文需要它作参数时，补充结构化参数字段（沿用 `ReasonKey`/`ReasonValues` 先例）。explain evidence 增加 `layerKey`/`statusKey`/`messageKey`+参数，`message` 字段保留。
- 前端：将 `check.code` 映射为 `productionReadiness.detail.<code>`（zh/en），参数插值；未知 code 回退渲染原始 `message`（新后端 + 旧前端 / 旧后端 + 新前端都不至于坏）。
- API 消费者（curl、AI agent）：行为完全不变。

**B 服务端多语言（Accept-Language 协商 + 后端消息目录）**：否决。翻译面翻倍、与控制台唯一 i18n 源（前端）割裂、API 响应随语言漂移损害日志可检索性。

**C 前端字符串事后映射（拿英文原文当 key）**：否决。脆弱，后端改一个词映射即失效，无法维护。

## 分阶段切片

**Phase 1 — 就绪检查 label 完整化 + nextAction code 化（已实施）**

实施时发现真实缺口比立项时判断的更窄也更隐蔽：`detail` 在界面上只作为未知 code 的兜底渲染（`t(labelKey, detail)`），真正露出英文的是两条路径——

1. **4 个就绪 code 没有 blocker label**（`application_capabilities_current`、`subject_scope_match`、`legacy_exact_equivalent`、`runtime_denied_trace_not_applicable`），主阻断行与其他待解决项直接兜底到英文 detail——评估 #12 看到的漂移句正是 `application_capabilities_current`。已补齐 zh/en 双语 label。
2. **nextAction 映射按英文原句整句匹配**（`productionReadinessCopy.ts`，即本立项否决的方案 C 的微缩版），后端 12 条消息有 2 条未命中（含漂移场景的 `reapply_permission_package` 与 `review_subject_scope`）。已改为按 `nextActionCode` 契约映射，新增 2 条双语文案；未知 code 回退原始消息（保留 sanitize 兜底）。

立项时设想的 `productionReadiness.detail.*` 键不再需要：detail 仅作未知 code 的兜底，原始消息兜底语义保留。护栏提前落地：`frontend/tests/productionReadinessLocalization.test.mjs` 从 `internal/httpapi/server.go` 抽取全部 blocking code 与 next-action code，断言前端 zh/en 双语覆盖——后端新增 code 而前端未跟随时测试失败。预检长尾核对完成：后端 10 个预检 code 前端 `permissionPreflight.detail.*` 全覆盖，无缺口。

- 验收（已通过，2026-09-19 隔离栈 E2E）：复刻评估 #12 场景——应用权限包后 PATCH 能力（区域/分级变更）制造漂移，readiness 返回 `application_capabilities_current` 阻断 + `nextActionCode=reapply_permission_package`；上线检查页主阻断行渲染「应用后，能力契约发生了变化。」，其余待解决项整句中文，页面文本扫描零英文整句。

**Phase 2 — 判定链键化（#16，已实施）**

实施结果（2026-09-19）：

- 后端：`managementMCPExplainEvidence`（`internal/httpapi/management_mcp.go`）新增 `messageKey` + `messageValues` 字段（16 个 key，3 条带参数），英文 `message` 原样保留——Management MCP 的 AI 消费者与 HTTP explain API（同一 result）行为不变；`layer`/`status` 本就是稳定 code，无需新增字段。
- 前端真实缺口比立项判断多三处：`ask.recordLayer.*` 缺 `caller_instance`/`target` 两个层名（评估 #16 看到的 "Caller Instance"/"Target" 直出即此）；`status.matched/missing/mismatch/inactive/not_approved/blocking` 六个状态标签全缺（"matched" 直出）；证据消息按英文整句匹配（`knownDecisionRecordMessages` 只覆盖 6 条静态句，带参数的 caller/target/capability 句永远命不中）。已全部改为 code-first：`ask.evidence.<messageKey>` 双语 16 条 + 参数插值；nextActions 改按 `nextActionCode` 映射（9 个 code，接口本就返回，句子映射保留为旧后端兜底）；未知 key 回退原句（保留 sanitize）。
- 护栏：`frontend/tests/accessDecisionLocalization.test.mjs` 从 `management_mcp.go` 抽取全部 messageKey/layer/status/nextActionCode，断言前端 zh/en 覆盖。
- 验收（已通过，2026-09-19 隔离栈 E2E）：复刻评估 #15/#16 场景——填 `user:support-doubao` 查询「查询客户」→ 判定链 6 环节点名/状态/细节整句中文（含带参数插值「调用方实例 L10n Caller 属于租户 default 和工作区 workspace-sandbox。」）；拒绝路径（未授权调用方）「缺失 · 调用方授权缺失，或正在阻断该能力。」+ code 化建议同样全中文；页面扫描零英文整句。
- 已知取舍：插值中的租户/工作区渲染原始 ID（`default`/`workspace-sandbox`），与 API 语义一致（后端传 ID），保持精确性；如需显示名，属后续参数增强。

**Phase 3 — 长尾与护栏（已实施）**

实施结果（2026-09-19）：

- 长尾排查完成：全库审计 `error.message` 透出路径后，用户可见的裸英文只剩一处——租户与组织视图的权限中心错误条（`permissionCenterError` 原样存 `error.message`）。已改走既有 `localizedErrorMessage` 兜底（zh 显示本地化文案，en 保留原文），与 `loadError` 同一模式。其余路径盘点结论：`loadError` 等状态早已走 `localizedErrorMessage`（非中文消息回退 key）；上线检查页 checkRows 四行均带 `detailKey`（`row.detail` 兜底不会触发）；连接自检面板的 `{detail}` 参数嵌在本地化模板内，属技术自检面，维持英文（与启动自检消息同口径）。
- 判定 reason 面加护栏：后端 reason 全部为静态句（store 层 14 条，memory/postgres 对齐），前端 `knownDecisionReasons` 恰好全覆盖。护栏测试做集合相等断言（后端新增 reason 未映射 → 红；前端死键 → 红）。后端 reason 键化（`reasonKey` 字段）暂不需要，留作 reason 出现参数化需求时的后续项。
- 防回归护栏（`frontend/tests/localizationLongTail.test.mjs`，4 项）：reason 集合相等；就绪渲染路径禁止裸用 `check.message` 作可见文案（labelKey 必须由 code 组合）；判定链渲染必须经 `accessDecisionRecordMessageLabel`（禁止 `{row.message}`/`{result.summary}` 直出）；`permissionCenterError` 必须走 `localizedErrorMessage`。

## 验收标准（总）

1. 中文控制台的上线检查页与访问查询页**零整句英文**（以豆包评估 #12/#15 场景回归为准）。
2. 未知 code 有可读兜底，前后端版本错配不产生空白或报错。
3. API 响应结构不变，英文 `message` 字段保留（curl/AI 消费者无感）。
4. 护栏测试进 `make check`。

## 风险与开放问题

- **双语文案维护成本**：14 code × 两语言一次性补齐，后续新增 code 必须同步三处（后端常量、zh、en）——护栏测试第 3 条用来卡住遗漏（后端出现前端未映射的新 code 时测试失败）。
- **参数化边界**：多数就绪消息是静态句；个别含动态 ID 的，倾向 detail 只描述性质、ID 已有独立 `evidenceId` 字段承载，避免过度参数化。工程设计文档里定死清单。
- **开放问题**：explain evidence 的 `status`（matched/missing/mismatch）是否与前端既有 `askJourney` 状态枚举统一为一套 key，实施时定。
