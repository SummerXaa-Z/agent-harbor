# 0.3.x Doubao console evaluation (2026-09-19, 2026-09-25)

Archived external evaluation record. The evaluator (Doubao 豆包 browser agent) ran two
rounds against local demo stacks on 2026-09-19: round one (report exported 02:46 local
time) covered the full console journey, the three security checkpoints, the consumer
leg, and a freestyle pass (findings #1–#8); round two restarted the stack in a fresh
state and probed boundary and failure paths (findings #9–#17, plus a correction of
round-one #2). A third round on 2026-09-25 re-ran the full journey plus regression
sections for the merged fixes and reported findings #18–#23. The reports below are
archived verbatim.

Environment notes for future readers:

- The report identifies commit `73472eb`, but both rounds served the live working tree
  via vite hot reload. Round one overlapped with in-flight fix work (final hmr 02:38–
  02:39, after the acceptance export at 02:35), so its checkpoints A/B "not reproduced"
  cannot serve as an independent pre-fix baseline. Round two ran later, with the #375 /
  #376 fixes already hot in the tree — its observation that the ask dropdowns populate
  once resources exist (#14 correction) reflects the fixed behavior, so round two
  doubles as partial post-fix verification. A clean re-run should start from merged
  `main` in a fresh checkout.
- Follow-ups: F-C/F-B fixed in #375; the go-live signal contradiction (#4 / F-E), ask
  scope empty dropdowns (#2), and token refresh staleness (#1) fixed in #376; the
  round-1/2 copy items (#5, #8, #12B, #13, #14) fixed in #378. Round-2
  note: #2's root symptom was the API returning no tenants for agents on the implicit
  default tenant, which is exactly what the #376 fix addresses. The localization gap
  (#12A, together with #16) is scoped in
  [`0.3.x-console-message-localization.md`](./0.3.x-console-message-localization.md).
- Open items after both rounds: #5 subject placeholder wording, #6 read-only audit for
  handoff view/copy, #8 「还差 N」counter wording, #9 refresh errors swallowed by the

  backend readiness/preflight messages hardcoded in English inside the zh UI,
  #12B inconsistent blocking counts (4 vs 3) on the go-live page, #13 duplicated
  period in preflight copy, #14 one workspace shown under two names, #15 optional
  subject left empty yields a false deny plus a repair CTA, #16 mixed-language access
  decision chain, #17 workbench not reconciling API-created approvals — plus pilot

## 3. 自由探索发现（步骤 / 现象 / 预期）

1. **[状态一致性] 撤销后 UI 不自动刷新**
   - 步骤：通过 API `DELETE .../tokens/{id}` 撤销令牌后停留在上线检查页。
   - 现象：令牌列表仍显示「生效中 · 09/19 03:12」；点「刷新交付」后才变「已撤销」。
   - 预期：撤销（无论来自 UI 还是 API）后列表应自动刷新或轮询，避免运维误判令牌仍有效。

2. **[自助性] 访问查询页下拉为空**
   - 步骤：进入「访问查询」(#ask)。
   - 现象：租户/工作区/调用方/目标/能力全部「暂无…」，提示「先完成资源接入」。
   - 预期：资源已注册并应用成功后，下拉应自动列出 default、Doubao Caller、Doubao Helpdesk MCP 等，而非空态引导。

3. **[失败路径-表现良好] 错误信息可诊断**
   - 被阻断能力 export_contracts → **403** `"access handoff token does not allow this capability"`。
   - 不匹配主体 user:sales-001 → **403** `"access handoff token does not allow this subject"`。
   - 未注册工具 delete_all_tickets → **403** `"capability is not registered for target"`。
   - 预期（已满足）：三类拒绝原因区分清晰。

4. **[文案/一致性] "可上线"信号互相矛盾**
   - 现象：上线检查页显示「3/4 通过」「上线阻断 1」（原因：当前浏览器会话尚未执行连接诊断）；而就绪报告 blockingCount=0、状态 ready。
   - 预期：会话级诊断门禁与数据级就绪结论应有明确说明，避免"报告说 ready、页面说有阻断"的困惑。

5. **[物料不一致] 主体占位符写法**
   - 现象：UI「预览技术细节」写具体示例 `user:support-example`；可复制 API 物料(copyArtifacts.mcpClientConfig)写通用 `<subject-id-matching-selector>`。
   - 预期：两处示例保持一致，或在可复制物料旁说明该值需替换为落在 `user:support-*` 内的具体主体。

6. **[审计覆盖] 查看/复制不留痕**
   - 现象：展开技术细节、点「复制」不产生审计事件。
   - 预期（安全视角建议）：高敏感交接卡的"查看/复制"至少应有只读审计事件，便于事后追溯谁取过接入材料。

7. **[非阻断] node 引擎告警**：v22.23.2 vs 期望 `>=24 <27`，仅 WARN。

8. **[进度文案]** 「还差 8 / 还差 7 / 还差 6」计数器语义不清（随步骤推进递减，未说明"还差什么"），建议改为明确的待办项清单。

9. **[失败路径-缺陷] 错误端点：UI 吞掉后端可诊断错误**
   - 步骤：注册指向死端口的 MCP 目标（`http://127.0.0.1:9999/mcp`），在「工具能力」点「刷新能力」。
   - 现象：界面只显示笼统的 **「无法刷新能力。」**，无任何原因。直接调后端 `POST /api/v1/targets/{id}/capabilities:refresh` 实际返回 **HTTP 502** `{"code":502,"error":"UPSTREAM_CONNECT_ERROR","message":"upstream connection failed"}`。
   - 预期：界面应透出上游连接失败原因（连接被拒绝/端口不通/超时），否则管理员无法区分是 URL 填错、端口错还是凭据问题。

10. **[自助性-缺陷] 多目标时配置默认选中"第一个 0 能力目标"，误导为"可直接应用"**
    - 步骤：同时存在 Bad Endpoint MCP（0 能力）与 Doubao Helpdesk MCP（3 能力），打开「权限变更 → 编辑配置」。
    - 现象：目标下拉默认选中排序第一的 **Bad Endpoint MCP**，导致预览 **「0 允许 / 0 拒绝」**，步骤 3 显示 **「可直接应用 该草案符合直接应用策略。」**；需手动改选正确目标。改选后立即变为「应用前需要审批」「更新工单 使用 写入 操作，需要先审批」。
    - 预期：0 能力目标不应给出"可直接应用"的肯定结论；应默认不选或默认到有已批准能力的目标，并提示"所选目标尚无可用能力"。

11. **[安全-表现良好] 服务端门禁与职责分离均强制，无越权旁路**
    - 无审批直接 `POST /permission-packages:apply` → **HTTP 400** `{"code":400,"error":"VALIDATION_FAILED","message":"permission package requires approval before apply"}`（UI 侧「应用权限」按钮在未审批时也为 disabled）。
    - 同一发起人批准自己的审批请求 → **HTTP 403** `{"code":403,"error":"PERMISSION_DENIED","message":"reviewer cannot resolve their own permission package approval request"}`（界面提示「生产环境会校验具名管理员身份，并强制职责分离」）。换 reviewer=security-approver 后才批准成功。
    - 重复应用同范围变更 → 预检拦截，界面原文「应用已被预检阻断：匹配的权限变更已经应用。请先查看当前状态，不要重复提交。」
    - 免审批策略安全：代码 `actionRequiresApproval` 规定仅当所有"允许"能力均为 read 时才可直接应用；任一 write/export/delete/admin 都强制审批，且判定基于能力实际 action、不由用户选择模板来规避——**找不到未经审批即可放大权限的入口**。

12. **[状态漂移-后端检出有效 / 前端呈现两处缺陷] 应用后修改能力分类**
    - 步骤：应用 `ppa_5e524e3e…` 后，把已应用能力 search_customer 的数据范围区域由「华东」改为「华北」(`PATCH /capabilities/cap_733253…`)，再查生产就绪。
    - 后端现象（符合预期）：检查 `application_capabilities_current` 由 passed 翻为 **blocking**，信息 "One or more applied capabilities changed after this permission package was applied."；`preflight_ready` 同步 blocking；readyCount **8→6**、blockingCount **2→4**、nextActionCode=`resolve_preflight_blockers`。区域改回华东后恢复。
    - 前端缺陷 A（**漏翻译/中英混杂**）：上线检查页头部翻为「已阻断 这次权限变更暂不能上线。」，但紧随的主阻断原因是**未翻译的英文原句** "One or more applied capabilities changed after this permission package was applied."；同页"其他待解决项"却已本地化为「请跑一次允许的生产调用。」。排查确认后端就绪/预检消息全部为硬编码英文（如 "Runtime allowed record is missing…"、"…does not contain an effective grant chain…" 等数十条），会原样进入中文界面，属**系统性本地化缺口**而非个例。
    - 前端缺陷 B（**同页计数自相矛盾**）：漂移后 Access Handoff 卡片文案写「仍有 **4** 项检查阻止交付。」，但其旁徽标与上方检查清单都显示「上线阻断 **3**」（4 = 后端 10 项细查口径，3 = 顶部 4 大类口径，两套计数未对齐）。

13. **[文案-缺陷] 双句号「。。」**
    - 现象原文：「应用已被预检阻断：匹配的权限变更已经应用。请先查看当前状态，不要重复提交**。。**」
    - 根因：模板 `message.permissionPackagePreflightApplyBlocked`=「应用已被预检阻断：{detail}**。**」会补一个句号，而内嵌 detail `permissionPreflight.detail.application_already_applied`=「…不要重复提交**。**」本身已带句号，拼接后重复。

14. **[术语一致性-缺陷] 同一工作区两处两个名字**
    - 现象：同一个工作区 ID `workspace-sandbox`，在「权限变更」流程里叫**「客户服务工作区」**（i18n `demo.permissionRequestWorkspace` / `text.defaultWorkspaceName`），在「访问查询」页工作区下拉里却叫**「运营工作区」**（i18n `demo.workspaceSandbox`，consolePresenters 把 "Sandbox" 映射为运营工作区）。管理员无法判断二者是同一个工作区。
    - 补充（修正第一轮发现 #2）：访问查询下拉在**真空态**才为空；资源注册后会正常填充，第一轮的"全空"是空态引导而非缺陷；真正的问题是本条命名不一致及第 15 条。
