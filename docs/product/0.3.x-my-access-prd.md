# 0.3.x My Access PRD

> 状态: Draft, 作为 0.3.x（My Access）立项执行 PRD。输入为 [0.3.x 产品设计评审](0.3.x-product-design-review.md)、[0.3.x 立项前最小实验结果](0.3.x-scoping-experiments.md) 和 [权限平台需求](0.3.0-permission-platform-requirements.md) §8/§9。
> 范围: 定义 0.3.x 可执行切片。工程级设计（schema、错误码、交互细节）开工前按仓库惯例补 `docs/engineering/0.3.x-*-design.md` 与 `*-plan.md`。
> 语言: 立项阶段中文优先；进入公开评审前按仓库惯例补齐中英双语。

## 一句话定位

0.3.x 要把"被拒的 Agent 凭证据申请恰好所需权限"变成产品回路。My Access 不是一张只读自助页，而是 **denial 驱动的 `request_access` API 契约 + 管理员裁决面 + flat 默认模式**——让消费侧第一次拥有不排队的恢复路径，同时不放松任何审批与审计纪律。

## 背景

v0.3.0 Phase 1（Access Handoff，PR #362）已随 `v0.3.0-dev-preview` 发布，验证了"权限变更完成后如何安全交付使用"。2026-09-19 的设计评审与两个立项前实验把消费侧的真实缺口量化了出来：

**管理侧成本基线（实验 1）**：交付一个能力给一个开发者需要 11 个管理步骤、16 次管理 API 调用。exact 低风险读权限已经免审批直接 apply——仪式成本已对低风险场景让步，剩下的成本来自链路本身的长度。

**消费侧事故基线（实验 1，发现 F3）**：5 类开发者事故全部终结于管理员——token 过期、token 撤销/丢失、需要兄弟能力（恢复需 ≥5 次管理调用）、查询自身授权、标准客户端无法连接。没有 `request_access` 回路、没有通知机制、没有个人可见面。

**可用性基线已修复（main 分支）**：进入本 PRD 前，实验发现的三个缺口已在 main 闭合——

- F1（#370）：网关本地合成 `initialize` / `ping` / `notifications/*` 协议生命周期响应，标准 MCP 客户端（Claude Desktop、Cursor、Cline、MCP Inspector、官方 SDK）带 handoff token 可完整接入。
- F4（#371）：交付卡片的 `X-AgentHarbor-Subject-Id` 写入通过 selector 校验的具体 subjectId，卡片自足。
- F3 前半（#372）：`GET /api/v1/self/access-profile` 个人可见面落地（任何 agent key 可读自身有效边界，评估口径与数据面一致；handoff token 被绑定收敛）；认证失败区分 revoked / expired（hash 命中才区分，猜测 token 保持通用错误，不构成探测 oracle）。

也就是说，"标准客户端能连、卡片自足、持凭据者可见边界、失败可诊断"的基线已经在 main。5 类事故中 2 类（标准客户端连接、查询自身授权）已关闭；**剩余 3 类（token 过期、token 撤销/丢失、需要兄弟能力）的恢复路径仍然全部是"找管理员"，这正是本 PRD 要建立的回路。**

**评审最重要的单条建议**：0.3.x 立项时把 `request_access`（denial 驱动、精确能力）作为 API 契约同期设计，不要做成纯 UI 自助切片。这是与 "AI-friendly permission operations" 定位直接相关的差异化能力，错过 0.3.x 的 API 设计窗口后补成本显著变高。

**复杂度基线（实验 2）**：Getting Started 六步、首日必须理解三级租户 + 四层授权链。flat 默认模式纸面原型已验证六步可收敛为三步，且与 fail-closed 语义无冲突点。

## 产品设计目标

1. **承接定位**: "AI-friendly permission operations" 的差异化一半在管理侧（已有 Management MCP），另一半在消费侧——被拒的 Agent 能凭 denial 证据自助发起精确申请，这是本 PRD 的核心。
2. **打开新市场**: 业务团队和集成开发者买的是"快速开通、清楚可用、少排队"。0.3.x 要让第二类买家第一次不经过管理员窗口就能推进自己的事故恢复。
3. **满足新需求**: 权限运营从"供给性交付"（v0.3.0）扩展到"消费侧回路"。审批、应用、审计仍在同一条控制链内，变化的只是请求的发起方。
4. **易用性优先**: 必要性复杂度（治理模型的代价）与披露复杂度（用户第一天必须消化的部分）解耦。flat 模式让新部署第一天不再前置租户树与授权链概念。

## 目标

### 产品目标

1. 数据面 Agent 能用自己持有的 agent key 提交 `request_access`：申请恰好被拒的那一项能力，附上 denial trace 证明，服务端校验证据真实性。
2. 管理员（或管理 Agent）能在请求收件箱里看到 pending 请求及其 trace 摘要，一键进入现有 exact 权限包草案链（draft → preflight → approval → apply → Access Handoff），或带理由拒绝。
3. 持有有效凭据的调用方能为自己死掉的手 handoff token 发起凭据续期请求，裁决后走既有 handoff 重签流程。
4. My Access 控制台页以 `GET /self/access-profile` 为数据锚点：边界、key 到期、最近 denied 记录与"申请此项"入口、我的申请列表与状态。
5. flat 默认模式进入 0.3.x：新部署自动创建默认租户/工作区，Getting Started 收敛为三步，层级语义按触发展开。
6. denial 聚合（评审 P6）与 `request_access` 同期设计数据结构（共用 denial trace），实现可后置到 v0.4。

### 非目标

1. 不做 IAM、SSO、登录或身份映射。`request_access` 以 agent key + subject 头为身份，管理员裁决即身份确认；身份源集成留给 Enterprise 阶段（需求文档 R2/R3 原口径不变）。
2. 不做 token 自助签发或自助续期。凭据的再取得永远经过管理员裁决；自动签发的前提（登录 + subject 映射）不成立于本阶段。
3. `request_access` 不绕过任何审批。高风险能力照走强制审批；请求只是把"排队"变成"带证据的队列条目"，不改变链路本身。
4. 不做自定义小集合包（评审 P4，v0.4 前再立项）和多资源权限包（v0.6）。本 PRD 的申请粒度就是单个能力（exact）。
5. 不做审批路由配置入产品（评审 P5，Enterprise 前任意时点执行，不阻塞本阶段）。
6. flat 模式不改 API 响应结构与治理语义，只作用于请求默认值与控制台呈现。
7. 不引入 email / webhook / 站内信系统。通知面收敛为控制台徽标、Management MCP 查询与自助轮询。

## 兼容性和升级契约

### `request_access` 是新增资源，不是授权链变更

请求对象（access request）是新的只读 + 状态机资源；裁决产物完全复用现有 exact 权限包链（draft / preflight / approval / apply / readiness / Access Handoff），不新增授权来源。`requestedCapabilityId` 端到端保留的既有语义（来源不回填）同样适用于请求发起的草案。

### flat 模式的 API 兼容立场（对应评审开放问题 3，实验 2 已定）

响应结构保持不变，flat 仅作用于：① 请求默认值——未指定 tenantId / workspaceId 时路由到部署期创建的默认对象；② 控制台呈现。flat 不产生新的兼容承诺。默认租户/工作区必须就是普通对象：事后可重命名、可挂父子，不做特殊的"扁平标记"实体。

### 既有接口不动

`GET /self/access-profile` 已在 main，是 My Access 控制台页的数据锚点，不再新增第二个自描述接口。401 的 revoked / expired 区分（#372）即消费侧诊断契约，本 PRD 不改错误码形状。

## 核心概念

### My Access / 我的权限

面向持凭据调用方的消费侧视图。0.3.x 之前它是 API（`GET /self/access-profile`）；0.3.x 把它控制台化，并接上请求回路：看见边界 → 看见 denied → 发起申请 → 跟踪状态。

### Access Request / 访问请求

数据面调用方发起的、带证据的权限或凭据申请。两类：

- **capability 请求**：申请恰好被拒的一项能力，必须引用真实存在的 denial trace（run/trace 归属同一 caller + subject，结局为 deny）。这是评审 P1 的本体。
- **credential_renewal 请求**：持有有效 agent key 的调用方，为自己已死（撤销/过期）的 handoff token 申请重签，引用 handoff 与死 key 的可识别信息（prefix）。完全没有有效凭据的调用方仍走管理员窗口——这是身份模型未落地前的诚实边界。

请求状态机：`pending → approved（进入权限包链）| rejected（带理由）`；pending 请求有 TTL 与去重合并。

### Denial Trace / 拒绝证据

既有的运行时拒绝记录（deny reason、run id、capability、subject、data-scope 判定）。0.3.x 起它承担第二个职责：作为 `request_access` 的证明材料。`request_access` 与 denial 聚合（FR-6）共用这一数据结构。

### 管理员裁决 / Adjudication

管理员或管理 Agent 对 pending 请求的处理：批准即从请求一键生成 exact 权限包草案，进入既有 preview / preflight / approval / apply 全链路；拒绝必须带理由，理由对请求方可见。

### Flat 默认模式

新部署的呈现层默认：自动创建默认租户 + 默认工作区（用户只填一个团队名），控制台隐藏层级语义。展开触发（单向累积，展开后不回退）：① 创建第二个租户；② 手动指定跨租户 dataScope；③ 打开任何"技术视图"开关。

## MVP 用户旅程

### 旅程 1: 被拒后凭证据申请（F3-B1 场景的闭合）

1. 开发者的 Agent 调用 `update_ticket` 被拒（403，handoff 只允许 `search_customer`），响应里带有本次拒绝的 trace/run 标识。
2. 开发者在 My Access 页看到该 denied 记录与"申请此项"入口；或 Agent 直接调用 `request_access` API。
3. 请求进入管理员收件箱，附 trace 摘要（谁、哪个能力、何时、为什么被拒）。
4. 管理员批准，一键生成 exact 草案，照走既有链（write/high 强制审批照旧）。
5. 应用就绪后走 Access Handoff 交付新 token；开发者在 My Access 看到新能力并首次成功调用。

成功标准：开发者从"看到 403"到"拿到可用 token"的全过程中，管理侧动作 ≤3 次（查看请求、批准、签发），对照基线的 ≥5 次管理调用 + 聊天往返。

### 旅程 2: token 死亡后的自助推进（F3-B3/B4 场景的收敛）

1. handoff token 过期或被撤销，调用返回可诊断的 401（`has been expired` / `has been revoked`，#372）。
2. 开发者用仍有效的 agent key 打开 My Access：key 到期时间可见、被拒历史可见。
3. 发起 credential_renewal 请求，引用死掉的 handoff。
4. 管理员裁决后走既有 handoff 重签（同一 handoff 同时最多一个活跃 token 的约束不变）。

成功标准：除了"完全没有有效凭据"的调用方（仍走管理员窗口，边界写明），其余死 token 场景不再需要口头/聊天渠道转述。

### 旅程 3: 管理员的请求收件箱

1. 管理员（或管理 Agent 通过 Management MCP）看到 pending 请求列表与计数徽标。
2. 每条请求展示 trace 摘要与请求方边界（caller、subject、现有效率、最近 denied）。
3. 批准 → 生成 exact 草案进入现有 Permission Changes 流程；拒绝 → 必填理由。
4. `access_request.created / approved / rejected / delivered` 审计事件全程留痕。

成功标准：裁决动作本身是现有权限包链的入口，不是并行的第二套审批。

### 旅程 4: flat 模式首次部署（实验 2 设计的落地）

1. 新部署，用户只填一个团队名；系统自动创建默认租户 + 默认工作区。
2. 三步完成首次成功调用：① 接入一个服务（target 注册 + 能力发现）② 选模板发起权限变更（草稿/审批/应用向导化）③ 验证上线（取证 + 验收报告）。
3. 首屏术语只有"团队、服务、权限包、审批"；entitlement / assignment 折叠进 Technical overrides。
4. 创建第二个租户时，租户树与层级语义展开，此后不再隐藏。

成功标准：三步内完成首次成功调用，期间不需要理解任何层级概念；展开触发后呈现与现状一致。

## 功能需求

### FR-1 `request_access` API

- 数据面 REST 端点，与 `/self/access-profile` 同组、同认证（agent key）、同限流策略：`POST /api/v1/self/access-requests`、`GET /api/v1/self/access-requests`（仅返回自己的请求及状态）。
- capability 请求必须携带 targetId + capabilityId（exact 单能力）+ denial trace 引用（runId/traceId）；服务端校验该 trace 真实存在、归属同一 caller + subject、对所申请能力的结局为 deny，否则拒绝请求（不可凭空申请、不可引用他人证据）。
- credential_renewal 请求携带 handoff 引用与理由；要求发起方持有有效 agent key。
- 同一 (caller, capability) 或 (caller, handoff) 的 pending 请求去重合并（重复提交返回既有请求），pending 有 TTL（默认 30 天，可配置）。
- 响应提供请求 id、状态与后续查询方式；错误契约沿用现有扁平 envelope 与稳定错误码。

### FR-2 管理员裁决面

- 管理端列表：`GET /api/v1/access-requests?status=pending`（按管理边界 scope），含 trace 摘要与请求方边界投影。
- 批准动作 `POST /api/v1/access-requests/{id}:approve`：生成 exact 权限包草案（`requestedCapabilityId` 指向所申请能力），跳转到既有 preview / preflight / approval / apply 流程；高风险审批门禁不变。
- 拒绝动作 `POST /api/v1/access-requests/{id}:reject`：理由必填，对请求方可见。
- 裁决权限遵循现有管理边界（tenant-scoped administrator 可见本租户请求）。

### FR-3 最小通知

- 管理端：控制台徽标（pending 计数）+ Management MCP 查询工具（`list_access_requests` 等，带既有安全/访问/生命周期/确认元数据纪律）。
- 消费侧：`GET /self/access-requests` 轮询 + 状态变化反映在 My Access 页。
- 不引入推送渠道（非目标 7）；推送集成留给 Enterprise 阶段。

### FR-4 My Access 控制台页

- 以 `/self/access-profile` 为唯一数据锚点：caller 身份、key 类别与到期、逐 target 能力边界（含 dataDomains / dataScopes）。
- 增加"最近 denied"区（引用 denial trace）与逐条"申请此项"入口。
- 增加"我的申请"区：状态（pending / approved / rejected + 理由）、对应的权限包应用与 handoff 交付引用。
- handoff token 登录时按绑定收敛展示（沿用 #372 语义）。

### FR-5 flat 默认模式

- 部署期自动创建默认租户 + 默认工作区，命名取用户填写的团队名；对象即普通对象（可重命名、可挂父子）。
- 未指定 tenantId / workspaceId 的请求路由到默认对象；响应结构不变。
- 控制台：首屏术语收敛为"团队、服务、权限包、审批"；租户/工作区字段折叠进 Technical overrides；三步 Getting Started 替换六步 checklist。
- 展开触发单向累积：第二租户、跨租户 dataScope、技术视图开关。
- 配套一等公民术语表与授权链可视化（评审 P2 的披露治理要求）。

### FR-6 denial 聚合数据结构（实现可后置）

- 与 `request_access` 共用 denial trace 结构，同期定 schema：按 (tenant, target, capability) 聚合的拒绝计数、最近拒绝、关联请求数。
- 聚合视图与批量"建议修复"（评审 P6 的运营工作台形态）实现可后置到 v0.4，但本阶段 schema 设计不得使其返工。

## 数据和接口建议

### 新增对象

- `access_request`：id、caller 实例、subject、类型（capability / credential_renewal）、targetId + capabilityId 或 handoffId、denial trace 引用（capability 类必填）、理由、状态、裁决人 / 裁决时间 / 拒绝理由、TTL、审计事件 id。不含任何 secret。
- denial trace 聚合投影（FR-6，只读）。

### 审计事件

`access_request.created` / `access_request.approved`（关联生成的草案 id）/ `access_request.rejected` / `access_request.delivered`（关联 handoff 交付 id）。沿用现有审计格式与敏感信息红线。

### 不变式

- 请求对象与审计不落明文凭据（一次性展示规则不变）。
- trace 校验失败、跨租户引用、伪造 runId 一律拒绝并留审计。
- 同一 handoff 同时最多一个活跃 token 的约束（既有）适用于重签。

## UI 需求

- 管理端：请求收件箱（徽标 + 列表 + trace 摘要卡片 + 一键起草 / 拒绝）；Permission Changes 流程入口不变。
- 消费侧：My Access 页（FR-4）；flat 模式下的术语与布局调整（FR-5）；术语表与授权链可视化入口常驻。
- 所有新页面沿用现有响应式与敏感信息脱敏纪律。

## 安全和合规要求

1. `request_access` 不提升权限：请求是证据 + 队列条目，授权仍只来自权限包链。高风险能力强制审批不可绕过（R3 原则）。
2. denial 证据服务端校验，请求面不构成探测 oracle：只能引用自己的 trace，列表只返回自己的请求。
3. 裁决动作全审计；拒绝理由对请求方可见但不泄露其他租户信息。
4. pending 请求防滥用：去重合并、TTL、每 caller 并发 pending 上限。
5. 凭据规则不变：短期、一次展示、可撤销、审计引用；任何新界面不展示明文 secret。
6. flat 模式默认对象不得弱化 fail-closed 数据域判定（跨租户 dataScope 触发展开即是此目的）。

## 指标

以需求文档 §9 口径为准，对照实验 1 基线：

- **消费侧**: My Access 到首次成功调用 < 5 分钟（§9 中期指标，外部评估实测）。
- **管理成本**: 每次能力交付的管理 API 调用数，对照基线 16；旅程 1 全过程管理侧动作 ≤3。
- **回路健康**: 被拒 → request_access → 裁决 → 可用 token 的端到端耗时与成功率；denied 记录发起申请的转化率；裁决耗时分布（管理员侧排队时长）。
- **自助边界**: 死 token 场景中经 credential_renewal 闭合的比例；完全无凭据场景（预期存在，边界透明）占比。
- **flat 模式**: 新部署到首次成功调用的步骤数，对照基线六步、目标三步；首日概念暴露数（评估人问卷口径）。
- **为 v0.4 预留**: 外部评估闭环开始记录"升级摩擦"（v1 应用迁到 v2 可用 token 的手工步骤数与耗时，评审 P3 口径），本轮只记录不建设。

## 验收标准

0.3.x 完成时，应该能演示：

1. 被拒 `update_ticket` 的开发者用 agent key 提交 capability 请求（附 runId），服务端校验 trace 通过、请求进入收件箱。
2. 伪造 runId、引用他人 trace、跨租户引用均被拒绝并留审计。
3. 管理员批准后一键生成 exact 草案，高风险审批门禁照旧生效；全链审计可查。
4. 应用就绪后 Access Handoff 交付新 token，开发者在 My Access 看到新能力并首次成功调用；旅程管理侧动作 ≤3。
5. 拒绝路径：理由必填、请求方可见。
6. 死 token 场景：可诊断 401 → credential_renewal → 裁决重签；同一 handoff 双活跃 token 仍被拒绝。
7. flat 新部署：只填团队名，三步完成首次成功调用；创建第二个租户后层级语义展开且不回退。
8. 新增 scenario 脚本覆盖 1–7，纳入 `make check` 与 `scenario-all.sh`；`make evaluation-readiness` 口径更新（消费侧指标纳入评估包）。

## 开放问题和推荐答案

1. **身份模型是否阻塞 `request_access` 先行？**（评审开放问题 1）
   推荐不阻塞。agent key + subject 头即身份，管理员裁决即身份确认；完全无凭据的调用方走管理员窗口是透明边界而非缺陷。登录 / OIDC / subject 映射留给 Enterprise 与后续授权生命周期阶段。

2. **`request_access` 的形态：REST 还是 MCP tool？**
   推荐 REST 先行（`/self/` 组，与 access-profile 同认证同限流）。理由：governed MCP 路由按 target 收敛工具面，而申请不是对某个 target 的工具调用；REST 面对脚本与 Agent 同样可用。MCP tool 包装形态（如面向 Agent 客户端的 `request_access` method）观察需求后补，不在本 PRD 承诺。

3. **flat 默认对象的命名与可迁移性？**（评审开放问题 3 由实验 2 收敛）
   推荐部署期由用户填一个团队名，生成普通租户 + 工作区对象；事后可重命名、可挂父子，无特殊标记实体。实验 2 已验证与 fail-closed 无冲突。

4. **混合数据域是否随本 PRD 放开？**（评审开放问题 2）
   不放开。它与 P4 自定义小集合包强耦合，v0.4 立项时一并定；本 PRD 申请粒度保持 exact 单能力。

5. **通知渠道边界？**
   本阶段只做控制台徽标 + Management MCP 查询 + 自助轮询。email / webhook 是集成能力，随 Enterprise 阶段的 SIEM / 通知体系一起设计。

6. **pending 请求的合并与过期策略？**
   推荐同 (caller, capability) / (caller, handoff) 去重合并 + 30 天 TTL + 每 caller 并发 pending 上限（默认 10，可配置），防滥用且不给管理员制造噪音。

## 结论

v0.3.0 解决了"权限变更完成后怎么安全交付使用"；实验证明交付后的世界还缺一半——被拒与失效全部终结于管理员排队，管理侧每单交付成本 16 次调用。0.3.x 用一个回路补上这一半：`request_access` 以 API 契约落地（不等待身份模型），裁决复用现有权限包链而非另起一套审批，通知只做最小面。flat 模式并行解开"第一天复杂度前置"的旧账。切片顺序的原则是回路优先于门面：先让被拒的 Agent 有路可走，再把路修得好看。
