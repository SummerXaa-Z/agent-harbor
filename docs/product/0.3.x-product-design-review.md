# 0.3.x 产品设计评审（2026-09-19）

> 状态: Design Review, 基于 `v0.3.0-dev-preview` 已发布状态，作为 0.3.x（My Access）立项输入。
> 范围: 产品设计与排序意见，不改变 v0.3.0 已交付契约。执行需求以后续 0.3.x PRD 为准。
> 语言: 评审阶段中文优先；进入公开评审或合入主文档前，按仓库惯例补齐中英双语。

## 1. 结论摘要

治理主线的设计纪律是真实优势，不需要调整方向：fail-closed 的数据域判定、来源不回填、一次性审批消费、验证记录文化。本评审的意见集中在**消费侧回路、复杂度披露、升级摩擦**三处，以及路线图中两处排序建议。

最重要的单条建议：**0.3.x My Access 立项时，把 `request_access`（denial 驱动、精确能力）作为 API 契约同期设计，不要做成纯 UI 自助切片。** 这是与"AI-friendly permission operations"定位直接相关的差异化能力，错过 0.3.x 的 API 设计窗口后补成本会显著变高。

## 3. 不应破坏的基线

评审先确认以下属性是优势，后续任何取舍不应以牺牲它们为代价：

- **Fail-closed 语义一致**：缺失、混合、矛盾、模板拒绝的数据域全部拒绝，能力分类跨 MCP 刷新持久。
- **来源不回填**：`requestedCapabilityId` 端到端保留，legacy 空字符串语义有明确判定规则，不为兼容改写历史。
- **证据文化**：验证记录、验收报告 digest、评估就绪包在多数同类开源项目中不存在。

## 4. 问题清单

每条标注问题类型：**新增缺口**（路线图未覆盖）或**排序意见**（路线图已覆盖，但时点或形态值得调整）。

### P1 消费侧没有请求回路（新增缺口，最高优先级）

**现状**：Access Handoff 的交付物是管理员签发、管理员屏幕一次性明文展示、再人工转交的短期 Token。Management MCP 的全部工具（draft / preflight / approve / apply / explain…）面向管理 Agent；平台愿景 §8 将 My Access 排在 0.3.x。

**问题**：被拒绝的数据面 Agent 没有任何自助通道。`explain_access_decision` 已存在，但反向的 `request_access`（附上 denial trace、申请恰好被拒的那一项能力）不存在。开发者 Token 过期后只能再找管理员走一遍。My Access 若只做 UI 自助，本质是把排队换了个窗口，没有建立"被拒的 Agent 凭证据申请恰好所需权限"的回路——这才是差异化故事。

**建议**：0.3.x My Access 立项时，`request_access` 与 UI 同期进入 API 契约。身份模型若是阻塞项，可先以"带 denial trace 证明的请求 + 管理员裁决"形式落地，不等待完整登录/身份映射。

### P2 复杂度是前置的，不是渐进披露的（新增缺口）

**现状**：第一天就必须理解三级租户树、四层授权链（capability → entitlement → workspace → instance）及每层 dataScopes 收敛语义；Getting Started 是六步 checklist；README 需要三段话解释空字符串的 exact/bundle 语义。

**问题**：必要性复杂度（治理模型的代价）与披露复杂度（用户第一天必须消化的部分）目前是同一个东西。十多个核心名词对新部署的首次成功调用构成直接摩擦，与 §9 短期成功指标（快速接入）相悖。

**建议**：**flat 默认模式**——新部署自动创建单租户单工作区、隐藏层级语义，第二个租户出现时才展开树形 UI 与 API 语义。这是不动治理模型的最便宜 UX 改造。配套在 console 提供一等公民术语表与授权链可视化。

### P3 仪式增长快于真实用户进入（排序意见）

**现状**：readiness 门禁、带 digest 的验收报告、评估就绪包、验证记录均按企业审计标准建设；目前所有验证者是"评估人"角色。v2 切换要求 reclassify → re-preview → re-approve → re-apply → re-issue 五步全手工。

**问题**：每增加一层 fail-closed 兼容规则，未来真实用户的升级成本同步上涨。仪式本身不是问题，**没有对应的降摩擦工具**才是问题。

**建议**：在下一轮评估闭环中增加"升级摩擦"指标（从 v1 应用迁移到 v2 可用 Token 的手工步骤数与耗时）；立项**升级助手**（启发式预分类能力 + 批量生成 re-approval 请求），优先级高于再加任何报告面。

### P4 两条申请道之间存在空档（排序意见）

**现状**：exact 道一次申请一个工具；bundle 道是固定模板，v2 模板还约束单数据域；多资源权限包排在 v0.6.0。

**问题**：现实请求是"三个读工具 + region=EU"，当前只能套整包模板（过度授权）或拆多次 exact 申请（流程税）。空档会系统性扭曲用户行为，且过度授权直接违背产品自己的最小权限立场。

**建议**：不必等完整多资源包（v0.6.0）。一个**自定义小集合包**（照走 preview / preflight / approval 全链路）在 v0.4 之前出现即可补上空档。需同步评估它与 v2 模板单数据域约束的关系（是否需要先支持混合数据域声明）。

### P5 审批路由的配置家分裂（新增缺口，低 urgency）

**现状**：管理员身份是产品内对象（Administrators & Boundaries），审批人路由在 `AGENT_HARBOR_APPROVAL_REVIEWERS` 环境变量。

**问题**："审批策略在哪配置"有两个答案，env 配置不可审计、不可走审批，会成为第一个"文档外配置"的坏先例。

**建议**：Enterprise 阶段前任意时点，把 routing 规则收进产品内、成为可审计对象。不阻塞 0.3.x。

### P6 拒绝被记录但未被运营（新增缺口，中优先级）

**现状**：trace 记录 deny reason，Access Query 支持点查与单点"发起权限修复"。

**问题**："哪个能力被拒最多、哪个租户在反复申请同类权限"的聚合视角不存在，而这恰是"权限运营"定位的日常工作面。

**建议**：denial 聚合分析 + 批量"建议修复"，把 Access Query 从查询工具升级为运营工作台。可与 P1 的 request_access 共用 denial trace 数据结构，建议同期设计。

### 小项

- **双语文档全量重复**：维护成本翻倍且已出现漂移风险；建议改为英文主文档 + 中文速览层。
- **README 信息架构**：Core Model 之后的千字段落实际无人读完；建议分"速览 / 深入 / 参考"三层重排。
- **定位表述**："不是 MCP 网关"的声明反复出现，恰说明市场会先按网关理解。建议一句话楔子，例如"Agent 时代的 IAM：管的是哪个 Agent 能用哪个工具碰哪些数据"。
- **前端主 chunk 超预算**：已知非阻塞，0.3.x 前值得清一次。

## 5. 与推荐路线的对齐

| 建议 | 对应路线位置 | 动作 |
| --- | --- | --- |
| P1 `request_access` API | 0.3.x My Access | 立项即写入 API 契约 |
| P2 flat 模式 | 未在路线图 | 建议纳入 0.3.x 并行 UX 轨 |
| P3 升级助手 + 摩擦指标 | 未在路线图 | 建议纳入 v0.4 授权生命周期前置项 |
| P4 自定义小集合包 | v0.6.0 多资源权限包 | 建议拆出轻量版提前至 v0.4 前 |

| P6 denial 运营视图 | 未在路线图 | 建议纳入 0.3.x–v0.4，与 P1 同期设计 |

## 6. 最小实验（建议在 0.3.x 立项前完成）

> 2026-09-19 更新：两个实验已完成，结果与发现见 [0.3.x-scoping-experiments.md](0.3.x-scoping-experiments.md)。最重要的新发现：受治理 MCP 路由默认拒绝 `initialize` 握手，标准 MCP 客户端全部无法接入（实验 F1），应作为 0.3.x 首个修复。

1. **开发者 persona 评估**：用 `make evaluation-readiness` 包，不给任何管理员协助，测 time-to-first-token 与第一个 blocker。直接量化 P1 / P2 的痛点程度。与 §9 已有"My Access 到首次成功调用 < 5 分钟"指标同一口径。
2. **flat 模式原型**：console 隐藏租户树跑一遍 core journey，验证六步 checklist 能否收敛到三步。纸面原型即可，不写运行时代码。

两个实验合计一至两天，结论直接决定 0.3.x 范围里 P1/P2 的优先级排序。

## 7. 开放问题

1. My Access 的身份模型（登录 / 身份映射）是否真的阻塞 `request_access` 先行？本评审倾向不阻塞（见 P1），需要立项时确认。
2. 自定义小集合包与 v2 模板单数据域约束的关系：是放开混合域，还是小集合包继承逐能力单域？
3. flat 模式下 API 语义如何呈现：隐藏层级但保持响应结构不变，还是提供简化响应形态？涉及兼容承诺，需在 0.3.x PRD 定。
