# AgentHarbor v2 重设计（2026-11-04）

> 状态: Direction decision，基于 v0.6.2（main e8c2257）已交付状态，作为 v0.7.0 起的重定向输入。
> 范围: 产品定位、形态与路线图原则。本文档改变方向，不改变任何已交付契约；工程执行仍走 issue / PR。
> 语言: 决策阶段中文优先；进入公开评审或合入主文档前，按仓库惯例补齐中英双语。
> 后续: 里程碑与验收标准以根目录 [ROADMAP.md](../../ROADMAP.md) 为准；M1/M2 关键构件的可施工设计见 [2026-11-v2-component-design.md](2026-11-v2-component-design.md)；逐分钟旅程、命令面、拒绝文案与控制台线框见 [2026-11-v2-ux-design.md](2026-11-v2-ux-design.md)。

## 1. 结论摘要

方向（agent 工具调用的权限治理）正确，核心资产（能力级判定逻辑、subject selector、data scope、带证据链的审计模型）有价值，但产品形态错误。v0.7.0 起把 AgentHarbor 从「自托管多租户治理平台」重定位为「agent 工具调用的权限与审计层」：默认单租户、配置即文件、执行点跟随生态、控制台降级为审计查看器与决策解释器。目标是让它先被一个真实用户（我们自己）日常使用，再决定下一步。

## 2. 诊断：旧形态错在哪

1. **执行点选错位置。** 网络中间人形态只能覆盖 HTTP MCP server；MCP 生态的执行点在往两端走（客户端侧 OAuth/权限模式、服务端 scope 校验），且大量 server 是 stdio 本地进程，网关在网络上看不见。这是形态层面的排他性约束，不是功能多寡问题。
2. **控制台成了产品本身。** 代码大头是治理 UI 旅程，建模了一个「治理运营岗」的日常工作流；小团队没有这个岗位（审批面是 PR/Slack），大企业有但用 ServiceNow/Okta。评估轮驱动开发放大了这一点：eval 给 console journey 打分，产品就长成了 console journey 的形状——为评估优化，不是为部署优化。
3. **多租户平台数据模型 ≠ 任何真实买家。** 租户→工作区→实例三层授权链是平台厂商卖给企业客户的模型；自用团队要「一个组织」，企业要把权限挂进已有 IAM。
4. **审批引擎是平行系统。** 权限包审批状态机与真实世界的审批（PR review、工单）重复。

## 3. v2 定位

**一句话**：Agent 工具调用的权限与审计层（the permission & audit layer for agent tool calls）。每个会碰真实工具的 agent 调用都需要三个回答——这个调用允许吗？依据什么？事后怎么查？AgentHarbor 负责回答这三个问题。

**目标用户**：先是我们自己（重度多 agent 用户），随后是让 agent 接触生产工具的小型自托管团队。明确不是企业平台买家。

**非目标（与旧定位的决裂）**：不做通用 MCP 聚合平台，不做企业 SSO/SCIM/多租户运营，不再投资治理 UI 旅程。

## 4. 形态：三种交付，一个内核

```
                    ┌─────────────────────┐
                    │  harbor-policy      │  判定引擎（抽取自 internal/domain）
                    │  Decide(req) →      │  纯函数：effect + evidence[]
                    │  effect+evidence    │
                    └─────────┬───────────┘
              ┌───────────────┼───────────────┐
     ┌────────▼────────┐            ┌─────────▼─────────┐
     │ harbor (server) │            │ harbor-wrap       │
     │ HTTP MCP 网关    │            │ stdio MCP 包装器   │
     │ 审计存储/查询     │            │ 本地判定+审计上报    │
     │ 控制台=查看器     │            │ 离线缓冲           │
     └─────────────────┘            └───────────────────┘
```

- **harbor（server，存量收缩）**：HTTP MCP 目标的网关与审计存储。保留执行面，砍掉平台面。控制台只保留两个一等公民：**审计查看器**（我的 agent 昨天干了什么）与**决策解释器**（为什么被拒，证据链）。
- **harbor-wrap（新）**：`harbor-wrap -- <stdio server 命令>`。包在任意本地 MCP server 外，工具调用经过时记录（进审计模型）并在本地用策略快照判定。这是对 stdio 半壁江山的回答。
- **harbor-policy（抽取）**：判定逻辑独立成库，server 与 wrapper 共用同一个心脏。不赌第三方采用——先有三个自己控制的消费者。

## 5. 设计原则

1. **单租户默认。** 首启动自动建默认租户/工作区，层级概念从界面隐藏（数据模型不动，多租户能力保留在 flag 之后）。单租户是现有多租户的退化情形，实现成本主要是默认值与界面。
2. **配置即文件。** entitlement / route policy 支持 YAML 导入（导出已存在于 management MCP），PR review 即审批流。控制台审批状态机降级为可选，不再是正门。
3. **执行点跟随生态。** HTTP 目标走网关，stdio 目标走 wrapper；不强求一个执行点覆盖两种世界。
4. **审计与解释优先。** 控制台的新投资只进这两个页面；其余治理视图冻结在当前状态（保留不删——作品集价值与未来可能性都在）。
5. **冻结而非删除。** apply→approve→go-live 用户旅程、权限包状态机、多租户 UI：全部冻结，不投入新代码，也不拆除。
6. **协议跟随 stateless 规范。** MCP 2026-07-28（SEP-2575）把方法与工具名提升为 HTTP 头（`Mcp-Method` / `Mcp-Name`），官方定位即「方便网关直接按头路由和鉴权」；harbor 的新数据面以 stateless 为主协议，能力级判定直接建在头信息上，网关无会话粘性、可水平扩展。存量会话式客户端与目标在过渡期内桥接。

## 6. 交互原则（2026-11-04 补充）

控制台不再是主界面。每个动作在离它最近的地方完成：

1. **改东西 → CLI 与文件。** `harbor import` 读取既有客户端 MCP 配置，注册 agent、给出起始策略建议、生成各客户端替换好端点的配置片段；策略变更走 PR review。上手衡量指标是 **time-to-first-audit-event**：目标五分钟内出现第一条审计事件。
2. **拒绝即解释。** deny 响应本身携带策略名、原因与 audit id（MCP 错误结构装得下），agent 与其主人在调用现场就能看懂；控制台负责深挖历史，不负责第一次回答。
3. **看历史 → 控制台（视角换轴）与 CLI 快查。** 审计时间线从治理运营视角（租户/层级筛选）换成「我的 agent」视角：默认按 agent 与时间组织，网关与 wrapper 事件汇入同一条时间线；高频查询提供 `harbor why <trace-id>`，不强制开网页。

控制台由「工作台」降级为「档案馆 + 深挖工具」；日常界面是 CLI 与错误消息本身。给构建者的产品，主界面就该在构建者待的地方。

## 7. 权限模型（2026-11-04 补充）

旧模型的复杂度不在叶子层——能力级 + subject selector + data scope 是差异化资产，原样保留——而在编排层（三层授权链：给一个 agent 开一个工具需要审批能力、补 data domain、填 6 字段表单、串行三次写入）。v2 权限模型四条：

1. **一次写入、一个对象。** 对外的 grant = `{agent, capability, 约束, effect}` 一条记录；三层链保留为内部存储与逐层审计账本（资产不动），但永不再出现在 API 与界面表面。
2. **工作区即信任边界，区内默认全通。** 边界是唯一的安全决策点（哪些目标、哪些数据域、哪些 agent 进圈）；区内能力默认可调，高风险调用（删除/导出/admin 类启发式）照常执行但在审计时间线上亮红标记。跨界访问永远需要显式授权。
3. **严格模式是开关，不是入场税。** 每个工作区一个 strict flag：翻开即默认拒，此时单条 grant 才生效。加固路径 = 先跑起来 → 看时间线上的红点 → 收紧 → 翻严格。旧 fail-closed 数据域强制收敛完整保留为严格模式语义，不再是所有人的默认姿态。
4. **治理按例外。** 能力不再需要逐个审批、补 domain 才可用；治理退为严格模式下的高风险/写操作待审队列。「导入即基线」：`harbor import` 把现状配置读为初始 allow 集，迁移不动现状，之后逐步收紧。

用户词汇表只剩一个概念：**工作区**。租户退化为自动开通的不可见常量（多租户层级随 flag 冻结）；实例绑定收纳进 grant 的 agent 字段。YAML 里开一项权限就是一行：

```yaml
agents:
  - id: codex
    allow:
      - capability: crm.lookupCustomer
```

## 8. 停止清单

- 新的外部评估轮（round-8 已跳过，维持）。

- 企业向特性（SSO、SCIM、多租户运营界面）——直到有真实客户提出。

## 9. 验收与退出条件

- **M1 验收即狗粮**：自己的 ≥2 个 agent 客户端的 MCP 流量全量过 harbor 一周；审计页能在 1 分钟内回答「我的 agent 昨天做了什么」。
- **诚实的止损线**：如果狗粮一周后我们自己都不想用它——停，封箱为作品集；如果 wrapper 证明 stdio 世界容纳不下——回退为纯审计模式（观测面），放弃执行面。

## 10. 与现有资产的对账

| 资产 | v2 中的角色 |
| --- | --- |
| internal/domain 判定逻辑（effective scopes、subject selector） | 抽取为 harbor-policy 内核 |
| 证据链 / 决策解释（evidence、messageKey 契约） | 最大差异化资产，控制台一等公民 |
| HTTP MCP 代理 + 能力发现（refresh） | 保留执行面；M2 以 stateless 规范（2026-07-28）重建数据面 |
| 双 store（memory/PG）+ 仓储接口 | 保留；M2 增加 SQLite 默认存储（单文件部署） |
| 治理控制台（旅程、状态机） | 冻结 |
| 25+ 场景脚本 / 评估基建 | 网关与 API 部分继续做回归；评估轮停止 |

## 11. 痛点与场景（2026-11-04 外部调研）

四类实证痛点，按强度排序：

1. **破坏性事故真实发生（最硬）。** 2025-07 Replit agent 在代码冻结期删除生产库及备份（SaaStr 创始人项目）；Cursor 上的 Claude「9 秒删库」；Claude Code 103 秒删除 4.8 万个真实文件。社区总结的解药——高危操作先问人、凭据隔离、工具调用审计——与 v2 的「默认放行 + 高危标红 + 严格开关 + 全程审计」同构。**边界诚实声明**：多数事故是裸 shell 而非 MCP 调用，harbor-wrap 只能包住 MCP server（如 filesystem server），是此痛点的部分解药，宣传口径不得全额认领。
2. **密钥裸奔最普遍。** [ReversingLabs 抽查过半 MCP server 依赖静态长期凭据](https://www.reversinglabs.com/blog/mcp-server-credential-weakness)；[arXiv 论文指出 MCP server 默认无沙箱、环境变量密钥可泄入 LLM 上下文](https://arxiv.org/html/2511.20920v1)；社区已在自造「MCP vault」轮子。harbor 网关模式的**客户端零密钥**（上游凭据服务端加密存储——internal/security 现成且已测——agent 只持自己的 key）是既有能力、从未被当作卖点表述；v2 叙事应明确打出。
3. **客户端配置方言最日常。** Claude Code 配置散布 5 处按优先级叠加、MCP 工具需逐个枚举授权、[managed-mcp.json 无法服务端统一下发](https://code.claude.com/docs/en/server-managed-settings)、第三方（PromptArmor 等）开始做跨客户端统一管理。一个 harbor 端点 + 一份策略文件 = 全客户端同一套规矩；`harbor import` 直接对准此痛点。
4. **企业网关赛道已拥挤（冷静项）。** Kong、Aembit、Tyk、Zuplo（十款对比）、Snowflake 均有 MCP 网关产品线。类别成立，但企业市场属于基础设施厂商；v2 的楔子是自托管、单文件、开箱即用与证据链深度，不参与功能对轰。

对应三个使用场景：**独狼多客户端统一管控**（M1 狗粮：Claude Code/Codex/Kimi 一个入口一条时间线）；**给 agent 生产访问权的团队**（事故规避：能读不能删、笔笔有记录、agent 变更一键吊销）；**事后追责**（审计：「上周二那个 agent 对计费库做了什么」一分钟内回答）。
